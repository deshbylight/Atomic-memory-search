# programming

## data-driven content and edit files
- [model] Store game data in editable text files, parsed into binary data for fast loading rather than code, so designers tune values without recompiling. Layouts: indexed, Markov-chained, table. When: Many content types should be editable, or custom variants and translations are planned; the engine must load data efficiently. Why: Text is easy to edit while binary loads quickly; tuning and variants need no code changes.
- [model] Spells can be stored as data: a name, mana cost, level, and an array of effects, each with a type enumeration and integer parameters, read by one generic cast function. When: Game needs many spells and frequent tuning; hard-coded tables suit small prototypes. Why: Adding spells requires no new logic, only new data entries.
- [definition] A merged effect family combines separate effect sets, such as melee blow effects and spell effects, into one shared set that all game elements draw on. When: Two existing effect systems do similar work and differ only slightly. Why: One shared set reduces the number of distinct code paths and test cases.
- [mechanism] An older version can load a newer save by mapping unknown types back to their preimages, which lets it read data it does not recognize. When: Saves created by a newer version are loaded in an older version. Why: The older version lacks the new identifiers, so unknown types need a fallback mapping.
- [mechanism] With one merged effect set, a single effect can be used by different sources, such as a trap causing hallucination or a trap causing gravity damage. When: Effects are shared across traps, monsters and items. Why: Shared vocabulary lets any source trigger any effect, so one effect can appear in many contexts.
- [rule] Move code into data only where the logic can be expressed as rows of data rather than separate code paths. When: Refactoring hard-coded game logic. Why: Data-driven rows are easier to maintain than special-case code.
- [rule] Design edit file formats so players can copy, paste, add and delete entries, with the game usually still working afterward. Why: Simple formats lower the barrier to player-made content.
- [rule] Split a game into engine, data and scripts so content can be imported into another rule set. When: Designing a game meant to be reused or extended by variants. Why: Separated data and scripts can be moved without rewriting the engine.
- [rule] Write each entry as an entry type, an angle-bracketed name, then information lines starting with an attribute keyword followed by comma-separated numbers or angle-bracketed strings; lines starting with # are comments.
- [rule] Avoid XML for game data files, because it is hard to write by hand, complex to parse and not compact.
- [heuristic] Use a default AI per creature type so wrapper AIs do not allocate new objects every turn. When: Creating many creatures that swap or wrap AI. Why: Repeated allocation and setup wastes time.
- [heuristic] Process item breaking last and use tail recursion, since exploding items can trigger further effects. When: Item destruction can cause new effects in the same action. Why: Running breakage last and recursing safely keeps chained effects from breaking the order.
- [heuristic] Keep deleted-content handling simple unless the game must still load old saves. When: Removing content from a game. Why: Full compatibility support is costly and needed only for saves that must still load.
- [procedure] 1) Change the text edit file. 2) Save it. 3) Restart the game so the compiled data file updates at startup. When: Customising a game through data files.
- [procedure] 1) Level 0 compiles the check out. 2) Level 1 silently returns. 3) Level 2 logs a warning and returns. 4) Level 3 reports an error with line number and exits. 5) Level 4 dumps the stack to a file and exits. 6) Level 5 raises a full assertion. When: Building checks that different distributions can configure. Why: Graded levels let each build choose how hard the program fails.
- [procedure] 1) Choose the affected grids with a shape function. 2) Apply the effect to that list with a separate effect function. 3) Apply movement effects last, after damage effects. When: Effects can damage and also move entities in a grid-based game. Why: Separating shape from effect lets regions reuse effects, and moving last avoids hitting the same entity twice.
- [procedure] 1) Consider inventing a new effect family. 2) Consider adopting one existing family. 3) Consider merging the existing families. 4) Choose the option that needs least compromise. When: Adding a new mechanic that needs a damage or effect type. Why: Each option has different code and balance costs, and no existing family may be clearly better.
- [procedure] 1) Parse each text edit file into its binary data file. 2) Reparse only when the edit file is newer than its binary file or the version number has increased. 3) Read the binary data at load time. When: Building a data pipeline from text edit files to binary data. Why: Skipping unchanged files saves load time while keeping data current.
- [procedure] 1) Make the format human-editable. 2) Make it easy for a parser to scan in one pass. 3) Make it compact. Why: These are the priorities in order when choosing a data file format.
- [procedure] 1) Play until design problems frustrate you. 2) Notice that data files are editable. 3) Add content to them. 4) Compile the code. 5) Release the modified version.
- [procedure] 1) List the systems the game already has. 2) Design new rules that reuse those systems rather than adding new ones. When: Adding strategic depth to a game late in development. Why: Reuse keeps scope small and builds on tested mechanics.
- [tradeoff] Indexed plain-data tables suit entries without logic; logic needs scripting, which is a large task, so early or time-limited projects may extend data files instead. When: Choosing a data format for game content; early project or limited development time. Why: Plain data tables are less expressive than scripting, but building a scripting processor is large.
- [tradeoff] Hard failure exposes faults where they occur, while silently continuing can corrupt state and fail confusingly later. Hard stops suit debugging; continuing suits shipped play. When: Choosing how code reacts to a failed internal check. Why: Silent continuation hides the fault's origin, making later failures hard to trace.
- [tradeoff] Merging is worthwhile when systems differ only slightly; forcing a merge when implementations differ greatly needs heavy compromises. When: Deciding whether to unify two existing systems. Why: Shared code only saves effort when the systems are close enough to share without compromise.
- [tradeoff] Importing whole 3D maps between engines is costly and often unreliable, because geometry, collision, navigation and scripts are implemented differently per engine. When: Moving level content from one engine or game to another. Why: A gap invisible in one engine can let characters fall through in another, and no common map standard exists for open worlds.
- [tradeoff] Shortening attribute keywords saves file space but reduces readability.
- [tradeoff] Publishers tend to avoid generated spaces because they cannot reliably control or censor every part of the game, while independent teams can accept less control. When: when deciding whether a studio should use generated game spaces.
- [pitfall] Unused effect parameters must be zero, and the end-of-array sentinel must be zero, so that C table initialization leaves unused slots correctly empty. Why: Uninitialized or nonzero leftover values make the cast function run unintended effects.
- [pitfall] Duplicating effect code across layers multiplies maintenance work, since each copy must be changed separately. When: Several effect layers handle similar logic. Why: Every fix or change must be repeated in each copy.
- [pitfall] Imported content may not fit a new rule set and must be reshaped to suit its world. When: Bringing monsters or other content from another variant. Why: Each rule set has its own assumptions about stats and behaviour.
- [fact] Plain data files are readable by players unless hidden by embedding them in the executable or inverting file bytes before distribution.
- [fact] Free, reusable art assets matter greatly to open source communities, because many programmers cannot draw. When: Developing open source games. Why: Programmers often lack art skills, so shared assets remove a barrier.

## actor state storage
- [mechanism] Creatures and the player on a moving platform are carried along; those able to stand on the platform terrain stay put, while others are pushed to an adjacent free grid. When: when a platform moves with occupants on it.
- [mechanism] Objects on a moving platform move with it; objects in its path are pushed and destroyed if no free grid exists. When: when a platform moves over objects.
- [rule] Update the flags on both the source and target squares whenever something moves, opens, closes, or a wall is tunnelled. When: Any change to a map entity or wall. Why: Updating only one square leaves stale FOV and movement results.
- [rule] Give items a standard set of operations: pick up, put down, wear or wield, use as weapon or ammo, eat or drink, use as container, break, and transform. When: Designing the item system of a roguelike. Why: A shared operation set lets new items reuse existing behaviour.
- [rule] Simplify item stacking to three rules: artifacts never stack, different kinds never stack, and different ego types never stack. When: Item stacking rules have grown numerous and hidden. Why: Many exceptions are hard for players to understand, so fewer clear rules reduce confusion.
- [rule] Apply movement effects after damage effects, so an entity moved into another affected grid is not hit twice. When: A permadeath game where effects can move the player. Why: Double hits from moving into an affected grid can kill a player unfairly.
- [rule] Store wand charges in their own value separate from the pval, rather than overloading one numeric value with several meanings. When: Items that carry several numeric properties. Why: A single overloaded value mixes unrelated meanings and complicates item data.
- [rule] Copy and translate a platform before moving it; if the copy would overlap terrain it cannot occupy, cancel the move.
- [rule] Pushed terrain assumes the underlying tile is empty floor, and monsters and objects on it move as for platforms.
- [heuristic] A per-square flag array for blocking, occupancy and visibility makes field-of-view and movement checks fast. When: Map checks run very often. Why: Flags answer per-square questions without scanning lists.
- [heuristic] Design map data structures around the operations run most often, such as FOV and movement checks. When: Choosing map storage for a game. Why: The dominant operation determines which layout is fast.
- [heuristic] Model traps as terrain features rather than separate data structures, so movement, pathfinding and door or trap code paths are reused. When: Adding traps to a game with terrain and pathfinding. Why: Reusing existing terrain code avoids duplicating logic for traps.
- [procedure] 1) Store terrain in a 2D integer array of indices into a terrain-kind table. 2) Store objects, items and monsters in lists, each entry holding its own position. 3) Keep a per-square flag array for fast checks. When: Structuring grid-based map data. Why: Dense data suits arrays while sparse, moving data suits lists.
- [procedure] 1) Store each item's numeric values in a small array. 2) Store the matching flags in a parallel bit array. 3) Pair each value with the flag it applies to. When: Items with several named numeric abilities. Why: Pairing values with flags keeps each number tied to its ability.
- [tradeoff] Actor state must live in actor data, usually via a switch on current activity, since actors rerun each turn; but storing all state there makes actor code harder to write. When: Writing actor behavior in a simple turn loop. Why: Actor code runs fresh each turn and cannot keep local state; state spread across data rather than held in code.
- [tradeoff] Keeping sparse objects in lists costs a scan to find what lies on a square, but avoids wasting memory and per-square updates when they move often. When: Choosing storage for sparse, moving map objects. Why: Scanning rare entries is cheap, while storing them per square wastes memory.
- [tradeoff] A compact array of values paired with flags uses less memory, while giving each flag its own integer costs more memory but has negligible speed cost on modern machines. When: Choosing how to store item numeric abilities. Why: Memory use differs, while modern hardware makes the speed difference negligible.
- [pitfall] Overlapping moving platforms can overwrite each other's stored terrain; linking platforms and moving them together prevents this. When: when multiple moving platforms share grid space.
- [pitfall] Continuous time handling in persistent world state can cause quantization bugs. When: when designing a persistent world with time-based state. Why: continuous values drift when stored and reloaded.
- [fact] A roguelike map holds four element types: terrain on every square, doors and traps as rare objects, items that may pile up, and usually one monster per square. When: Designing map data for a grid-based game. Why: Each type has a different density, which dictates its storage.

## line of sight and visibility
- [model] Full field-of-vision algorithms include ray-based casting, occlusion sweeps, angle-limited precise shadowing and permissive field of view; an efficient observation refinement may visit fewer squares.
- [mechanism] Line of sight and line of fire can disagree, so a grid may look untargetable when aimed at directly yet be hit when aiming at a nearby grid; show this difference in targeting UI or show the projectile failing.
- [rule] Model light as a sphere rather than a circle when the game has vertical levels. When: Computing what a light source illuminates in a game with height. Why: A circular light on a roof misses areas beside walls below it.
- [rule] Exit target mode by pressing the target key again, or automatically when targets die, the weapon runs out, targets leave range, or the player leaves range or line of sight.
- [heuristic] Lighting the whole level or lighting only the room the player occupies are simple visibility options; room lighting suits maps made of rooms joined by corridors. When: Maps built from rooms and corridors, or when full map visibility is acceptable. Why: Room structure lets a cheaper method replace full line-of-sight calculation.
- [heuristic] Targeting is less of a problem in turn-based games, because monsters act only after the player's action. When: Turn-based games. Why: Monsters do not act during the player's targeting.
- [heuristic] Use a full targeting system when projectiles and spells need precise targets, since it makes ranged combat simpler for the player. When: Ranged combat with projectiles or spells.
- [heuristic] Prefer a top-down or 2D view when units span several height levels, such as air and ground mixed together.
- [procedure] 1) Iterate the monster or object list. 2) Filter entries by distance. 3) Check line of sight for the remaining entries. When: Finding nearby monsters or objects to a position. Why: Iterating a sparse list is cheaper than scanning every square.
- [procedure] 1) When there are more targets than ids, assign ids by priority. 2) Holding Shift adds a third key that doubles the number of available ids. When: More targets than available single-key ids.
- [procedure] 1) Ctrl-click selects a single unit. 2) Shift-click selects a range. 3) Ctrl-number assigns a group, following the RTS convention. Why: Modifier keys give quick selection when a top-down view is not used.
- [tradeoff] Fixing the overlay can use a side list, placing the id beside the letter, or blinking; each option has its own costs. When: Target ids hide monster glyphs.
- [pitfall] Per-square line-of-sight checks repeat much of the same work and are slow; computing the field of vision as a whole avoids that repetition.
- [pitfall] An id overlay can hide the monster letters the player needs for tactics. Why: Ids are drawn over the map.
- [pitfall] In crowded areas, side-by-side ids can be hard to read. When: Dense groups of targets.
- [fact] Making monsters invisible can be simple when line of sight is built in a particular way, while making them die can be harder. When: Implementing invisibility on top of an existing line-of-sight system. Why: Existing visibility code may already support hiding entities.
- [fact] Some roguelikes ask only for a direction, while others have a full targeting system for spells and projectiles.

## save file format and integrity
- [mechanism] Give each changed content type a new identifier that keeps a link to its earlier form, called a preimage, so old saves can be converted when they load. When: Content such as monsters or items changes between game versions. Why: Old saves reference types that no longer exist in their original form, so a mapping is needed.
- [mechanism] Persistent world changes need memory, and tracking persistent object interactions adds complexity, so many games fake persistence. When: when designing persistent game worlds. Why: storing every change is costly.
- [rule] Save files should load across machines, operating systems and versions, since portable saves enable bug reports, tournaments and sharing.
- [rule] After changing the parser or data structure types, delete the compiled binary data files, because stale data can crash the game or corrupt saves. When: The parser or data structure definitions change. Why: Old binary data no longer matches the new structure layout.
- [procedure] 1) Store the random number generator state. 2) Keep the generator in your own code. 3) Write plain UTF-8 text. 4) Store objects in hash tables by ID and reference them by ID. 5) Delimit sections with start and end markers, not length prefixes. 6) Check every value read from disk and replace impossible ones with defaults, warning the player. 7) Give content types version-stable IDs. 8) Ignore unknown sections. 9) Warn before version conversion and let the player refuse it. When: when cross-platform loading or sharing matters.
- [procedure] 1) Map each old type to its new identifier. 2) Convert old types to new ones when a save loads. 3) Optionally add new types during restore, weighted by rarity (diversifying conversion). When: Loading saves created by an earlier version of the game. Why: Keeps old saves playable after content changes.
- [procedure] Encrypt the move record with an asymmetric key so that only the tournament server, holding the private key, can decrypt and verify it. When: Tournament or server-verified play must hide the move record from clients. Why: Clients can read a symmetric key and forge or rewind records.
- [procedure] 1) Store words with tags such as subject, verb, object, adjective, and status. 2) Assemble the sentence from tags with a builder function. 3) Drop words at lower verbosity levels. When: Generating game messages.
- [tradeoff] Deleted content can be kept forever, mapped to a postimage in a replacement table, or kept as a hidden replacement that spawns only from old saves; simpler options suit games that need not load old saves. When: Content is removed from the game. Why: Each option balances save compatibility against code and data maintenance.
- [tradeoff] Recording every move lets a server replay a game to verify it, but a readable move record also enables arbitrary rewinding. When: Verification of competitive or shared-score games matters. Why: The same record that enables verification also gives players a way to undo moves.
- [tradeoff] Hashing a save with a secret key makes tampering harder, but the key can leak from the client, so the protection is limited. When: Client-side saves must be protected against edits. Why: Anything the client holds can be extracted.
- [tradeoff] Tagged word building is more modular and flexible, while indexed lists of whole sentences are simpler but less modular.
- [pitfall] References to removed targets dangle: ID-based hash lookups return null and must be null-checked, and destroyed objects referenced from several structures must be cleared from them. When: Objects are referenced from multiple structures or looked up by ID. Why: Destroyed or missing objects are not cleared from other references, so lookups can return null.
- [pitfall] Length-prefixed save sections can fail entirely after one corruption or manual edit, while end markers confine the damage.
- [pitfall] Parse checks catch malformed entries, but bounds checking is light, so invalid data values can crash the executable. When: Editing data files without code. Why: Light validation lets out-of-range values reach the engine.
- [pitfall] Editing data files can still break a game, so edit formats should tolerate mistakes gracefully.
- [fact] A stack dump written to a file lets players without debugger skills report where a failure occurred. When: Releasing builds to users who cannot attach a debugger. Why: The dump records the call path at the failure point, which bug reports can include.

## spell casting and targeting
- [model] Each spell is a struct combining an effect function pointer, an area, and a target; new spells mix properties freely instead of hard-coding each one. Why: Shared properties remove duplicated code across similar spells.
- [definition] A pval is the numeric value tied to an item flag, such as the bonus a ring gives to a stat.
- [rule] Use a separate hierarchy when spells need target types beyond map coordinates, such as inventory items, since a single coordinate target is too narrow. Why: Item targets need data the coordinate model lacks.
- [rule] Keep item selection separate from item creation, so one weighted generator can choose item types, monster types or map types.
- [heuristic] Start spell data in a hard-coded table, then move to an external data file once tuning becomes frequent. When: Early prototype stage moving toward heavy balancing. Why: External files speed iteration without recompiling.
- [procedure] 1) Receive spell, caster and target. 2) Log the cast. 3) Run each effect in the spell's array in turn. 4) Stop at the zero-type sentinel that ends the array. Why: A single cast function interprets all spell data.
- [procedure] 1) Get the target. 2) Find all squares covered by the area. 3) Apply the effect to each square, including any creature or item there. Why: A common path handles all spell shapes.
- [tradeoff] A minimal effect record suffices early, but target type, timing, and caster or target flags are likely to be needed later. Why: Extending a data format after many entries exist is costly.
- [tradeoff] Fixing ball and beam radius in code is too constraining; range and power should be parameters. Why: Parameters let one spell design scale to different situations.

## automated stress testing
- [definition] An automated player bot runs long sessions that exercise many code paths, so it can reveal crashes and infinite loops even in variants too complicated to play by hand.
- [rule] Make summon-cull checks cheap, because summon checks run frequently inside monster AI. When: implementing summon limits in monster AI. Why: Frequent expensive checks slow the whole game loop.
- [rule] Raise the maximum entry limits in the limits file before adding entries past existing caps, since these limits also set per-level monster and object counts and text memory. When: Adding entries to data-driven game content. Why: Caps are fixed in the limits file, so new entries fail without raising them.
- [pitfall] Systems with limited memory or performance need failure checks compiled out rather than left running at runtime. When: Targeting constrained hardware or tight frame budgets. Why: Runtime checks consume memory and time that constrained systems cannot spare.
- [pitfall] Testing every position against every room size is slow at large scale. When: when placing rooms in a large dungeon. Why: exhaustive search scales poorly.
- [fact] Cheating cannot be fully stopped, only made harder; keystroke logs can be captured by the operating system.

## absorbing code exceptions
- [procedure] 1) Identify special-case code paths. 2) Add a flag that marks each special case in the data files. 3) Move the case into data so the code path can be removed. When: A data-driven codebase has accumulated exceptions.
- [tradeoff] Specialised hacks give abilities distinct play but multiply maintenance cost, so each hack should earn its place in play. When: Deciding whether to implement a special-case ability effect. Why: Each special case must be tested and kept working alongside the rest of the code.
- [pitfall] A loosely held patchwork of code exceptions accumulates, and each exception persists until it is moved into data. When: Maintaining a codebase with a data-driven core. Why: Exceptions left in code resist the data-driven design.

## damage source logging
- [rule] Log damage and effect sources separately, such as direct hits versus damage over time, so item and monster comparisons are meaningful.
