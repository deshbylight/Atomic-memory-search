# algorithms

## game turn scheduling
- [model] Each timed entity has a current time value, a rate callback returning its speed, and a cost callback that runs its action and returns the action cost.
- [model] Timed entities form a circular doubly linked list with a traveling sentinel marking start and end; the sentinel advances one step per tick, so the list rotates like a queue.
- [model] In a player-centric loop, the main loop runs the UI and calls a world-update function only for player actions that take a turn; it is simple but inflexible, and may suit animation-heavy games. When: Building a small, animation-driven roguelike. Why: Only player actions drive the world forward.
- [model] In a simple turn loop, the main loop iterates over all actors each turn, asking each for an action and running it if possible, which supports many actors with different speeds. When: Building most roguelikes with many actors. Why: Every actor gets a chance to act each turn.
- [model] An entity component system builds game objects from a unique ID plus separately stored components, combining traits by composition instead of deep inheritance. When: Designing object structure for a complex roguelike. Why: Deep inheritance hierarchies become hard to maintain, while composition mixes traits freely.
- [mechanism] An actor can spend accumulated energy at once to interrupt a wait. When: Designing wait or delay actions in an energy-based system. Why: Stored energy lets an actor act sooner than its regular rhythm allows.
- [mechanism] Different actions can have different delays, such as attacks taking twice as long as walking, changing the turn order.
- [mechanism] Each tick a timed entity's speed is added to its time value; while the value is non-negative, its action cost is subtracted and an action runs, so faster entities act more often. Why: Speed differences are felt as differing action frequency.
- [mechanism] Components are stored in containers keyed by entity ID; querying for entities with a set of component types is the intersection of the sets holding each component. When: Finding all entities that have several components. Why: Intersection gives the matching IDs without scanning every entity.
- [rule] Compute action delay as base delay divided by speed, guarding against division by zero; each creature's turns per cycle then equal its speed, giving a fixed turn ratio. Why: Faster creatures get shorter delays and proportionally more turns, so relative speed gives a predictable ratio.
- [rule] Remove a timed entity only from inside its own rate or cost callback.
- [heuristic] Use a player-centric loop for small, animation-driven games and simple turns for most roguelikes with many actors of differing speeds. When: Choosing a turn loop architecture. Why: Each loop suits a different scale of actor activity.
- [procedure] 1) Insert each creature, including the player, with its action delay as priority. 2) Pop the lowest-priority entry. 3) Subtract its priority from all remaining keys. 4) Let it act. 5) Re-insert it with a new delay. When: Ordering actor actions in a turn-based game where actions have different durations. Why: Placing actors by action duration lets fast and slow actions interleave correctly; time advances without a fixed tick.
- [procedure] 1) Mark the actor as busy. 2) Check for interrupts. 3) Update the action counters. 4) Return control to the loop. When: An action such as eating takes several turns. Why: The loop resumes the action each turn without blocking other actors.
- [procedure] 1) Settle time handling: turn order, scheduled events, interval effects, and speed or freeze changes. 2) Settle map representation, save and restore, ranged effects, area effects, timed map changes, pathfinding, field of view and generation. 3) Define standard item operations. 4) Define standard places for new behaviour and effect values. When: Before adding much content to a roguelike. Why: Changes to time or space representation later force rewrites across most existing code.
- [tradeoff] Energy each tick: act only with enough energy, paying cost immediately; or act while energy is above zero, paying cost afterward and allowing overshoot. When: Making actor speed a continuous stat, where energy regained per tick depends on a customizable game speed. Why: Faster actors accumulate energy quicker and act more often; overshoot keeps timing consistent over time.
- [tradeoff] Use a queue when actions have different durations and interrupts matter; use an energy system when speed should be a continuous stat. When: Choosing an action scheduling model for a turn-based game. Why: Queues handle variable durations and interrupts; energy handles continuous speed.
- [tradeoff] A linear sorted insert into the open list is simple but costs more on large maps than a binary heap. When: Implementing the open list.
- [tradeoff] Slow actors can wait several turns and fast actors can act more than once per turn, but this handling is messy. When: Actors have different speeds in a simple turn loop. Why: Speed differences must be simulated by skipping or repeating turns.
- [pitfall] Interrupt logic using watchers adds significant complexity to a scheduling system. When: Adding interruptible actions to a queued turn system. Why: Each action must notify and check watchers, increasing state to manage.
- [pitfall] Re-queuing a node with a better cost requires removing its old entry from the open list first. When: Updating a node already in the open list. Why: Leaving the stale entry causes duplicate processing.
- [pitfall] A minimal component registry without caching is for understanding only, and is too slow for production use. When: Implementing a first entity component system. Why: Missing optimisations such as caching cost time on every query.
- [pitfall] Reducing all game objects to one generic entity is discouraged, because the effort shifts into designing the type system. When: Choosing how to structure game data types. Why: A single generic type pushes complexity into type design rather than removing it.
- [fact] A turn scheduler can store any timed event, such as regeneration, hunger, spell or enchantment effects, one-time time bombs, calendar time, or creature actions.
- [fact] Some actions, such as opening inventory, do not consume a turn.
- [fact] Values such as monster level, rarity and experience can be computed by algorithm and written out to a user data folder. When: Game values are derived from formulas rather than typed by hand. Why: Computed values can be inspected and reused without manual entry.

## pathfinding
- [model] Movement variants include crab movement (fast sideways, slow vertical), turtles retreating into a high-defense shell, and territorial patrolling. When: Designing distinctive monster movement.
- [definition] With f equal to path cost from start, the search is Dijkstra; with f adding a distance estimate to the goal, the search is A*. When: Choosing between Dijkstra and A*.
- [rule] Rebuild distance maps only when goal points change, not every turn, since recalculation is costly; tune the update interval for many pathing agents. When: Maps used by many monsters or many pathing agents. Why: Recalculation is costly and goals change less often than turns pass.
- [rule] Do not use the first-labeled-is-minimum flood method when terrain has different step costs, since it needs updates to queued squares. When: Terrain with varied movement costs. Why: First-label minimality holds only when all steps cost the same.
- [rule] Use A* when the goal is known and a good distance estimate exists; use plain Dijkstra when no useful estimate exists or many paths from one source are needed. When: Selecting a search algorithm.
- [rule] Give flying and walking creatures different costs for moving up or down. When: Designing movement rules for creatures in a multi-level game. Why: Flying and walking creatures should not have identical vertical movement.
- [rule] Use A* or Dijkstra limited to the field of view for terrain with movement costs, rather than wall following. When: The map has varied movement costs. Why: Wall following ignores costs, while cost-aware search handles them.
- [heuristic] Prefer cheap approximations such as flow-by-scent or flow-by-noise over exact route finding, since exact routes multiply computation and break when terrain changes. When: Monster pathfinding over varied terrain. Why: Per-terrain exact flows grow with each terrain trait combination and must be recomputed when terrain changes.
- [procedure] 1) Label the origin. 2) Repeatedly label unlabeled neighbours with the current label plus one, queuing them. 3) Stop when the target is labeled. 4) From the target, step to the neighbour with one lower label until the origin is reached. When: Shortest path on a grid where every step costs the same. Why: First-in first-out labeling gives each square its minimum label on first assignment.
- [procedure] 1) Create an empty priority queue and an empty visited set; push the start with its cost. 2) Remove the lowest-f node; succeed if it is the goal, fail if the queue empties. 3) For each successor, compute f as parent f plus step cost and add or update it when unvisited, queued with higher f, or visited with higher f. When: Implementing a best-first grid or graph search.
- [procedure] 1) Build the distance map from the player. 2) Multiply every value by about -1.2. 3) Rescan the map. Monsters then step downhill, running toward distant cells and doors. When: Monsters must flee the player. Why: Inverting the values turns the nearest-goal gradient into a run-away gradient.
- [procedure] 1) Treat every undiscovered cell as a goal. 2) Build the distance map. 3) Move the player downhill. 4) Stop when a message appears or a new monster comes into view. When: Automated exploration of a level.
- [procedure] 1) Step directly toward the goal while the line is clear. 2) When blocked, switch to wall following and record the blocking cell. 3) Stop following when closer than the smallest distance recorded so far. 4) Abort after four times the sight range in steps. When: A monster must find a path knowing only its own sight and the goal coordinates. Why: Wall following reaches goals without a full map, and the step limit stops endless loops when no path exists.
- [procedure] 1) Define the threat or hazard that changes mid-route. 2) Re-evaluate the agent's options when the terrain changes. 3) Compare advancing, retreating and waiting by expected outcome. 4) Include the agent's current and future state, such as health and fire resistance. When: Testing a pathfinder before implementing dynamic hazards such as spreading fire or flooding. Why: A static path can walk an agent into a newly created hazard, so decisions must reflect changed terrain and agent state.
- [tradeoff] Moving monsters may add no path cost so traffic follows shortest routes, but treating monsters as passable in A* tends to pile them at chokepoints. When: Pathfinding with monsters as costs; crowded corridors and doorways. Why: Idle counters are zero while moving.
- [tradeoff] Heat-based search is unreliable when the player can move far in one turn, such as by teleporting or blinking. When: Player has long-range movement. Why: The per-turn spread cannot keep up with large jumps.
- [tradeoff] Wall-following pathfinding is faster than A* on large maps and needs little monster state, but it cannot handle movement costs and can produce long paths. When: Choosing a pathfinder for large maps with uniform movement. Why: It trades path optimality and terrain costs for speed and low memory.
- [pitfall] The estimate-based ordering only holds if the heuristic never overestimates the remaining cost. When: Using A* with a distance estimate. Why: An overestimate can make the search return non-optimal paths.
- [pitfall] Treating unexplored cells as passable can route paths into walls, so pathing should stop when the error becomes clear. When: Pathing over partly revealed levels. Why: Unknown cells may actually be solid.
- [pitfall] Dynamic terrain and temporary states make a single correct pathfinder very complex, so simpler heuristics are often needed. When: Pathfinding must account for changing terrain and temporary states. Why: Modelling every state combination quickly becomes intractable.
- [fact] When no path exists, a breadth-first flood covers every reachable square before failing. When: Target is unreachable.
- [fact] Chebyshev distance counts diagonal and straight steps equally, so crossing an 80x25 map corner to corner takes 80 steps. When: Measuring grid distance when diagonal moves are allowed. Why: Diagonal steps cost the same as orthogonal ones.

## distance heuristics
- [definition] Chessboard distance between two cells is the larger of their horizontal and vertical gaps, so a diagonal step costs the same as an orthogonal step. When: Grids where diagonal moves are allowed at equal cost.
- [procedure] 1) Measure planar distance. 2) Measure height difference. 3) Distance = larger of the two plus half the smaller. When: Computing distance between entities on different elevations in a grid roguelike. Why: Gives a usable distance estimate that accounts for both horizontal and vertical separation.
