## room and corridor layout
- [model] Abstract dungeon areas can be generated by three methods: a uniform grid for regular structures, recursive subdivision for most fantasy dungeons, and custom growth from a corridor for symmetric layouts. When: choosing how to lay out areas before walls are drawn. Why: Each method produces a different structure suited to different settings.
- [model] Room types include lakes, waypoints, overlapping rooms, starburst rooms, fractal rooms, maze rooms, chambers, lairs, vaults and towers, each with its own layout algorithm. When: Designing a multi-generator dungeon layout system. Why: Different algorithms give different room shapes and purposes.
- [model] Room-and-corridor layouts provide four features: corridors as choke points with cover, convex rooms where everything is visible, concave spaces that hide things, and loops that let a player escape same-speed enemies. When: Designing or generating room-and-corridor layouts for tactical play. Why: Each shape supports a distinct tactical function, and together they produce varied combat and escape options.
- [definition] A standard dungeon is a subterranean maze of rooms joined by corridors and stairways, where each level becomes more dangerous and more rewarding.
- [mechanism] Splitting some parts more deeply than others produces smaller rooms in those parts, so one level can mix room sizes. When: varying room sizes within a BSP-generated level. Why: Deeper recursion yields more and smaller leaves in that region.
- [mechanism] Running the row-walking carve several times on one map yields overlapping paths that cross and rejoin, and varying the direction removes any single consistent direction. When: Combining multiple carve passes on one map. Why: Each pass adds an independent winding path that may intersect others.
- [mechanism] Flood fill from a central seed gives a fan-shaped corridor layout with backtracking, while connecting each room to the last one gives many loops.
- [mechanism] Corridor length, width and twistiness, and whether rooms are clear or cluttered, determine how useful each attack shape is, so generated layouts change balance. When: generated dungeon layouts.
- [mechanism] Connectors can be opened as doors, open passages, locked doors or other features, so one connection step creates varied passage types. When: when deciding passage types between regions. Why: the connection step is separate from the passage style.
- [rule] Generated levels should use a grid or cube layout so that the same movement and interaction rules apply everywhere. When: Generating roguelike levels. Why: Uniform space keeps one rule set valid throughout.
- [rule] Keep split positions away from the border so each part can still hold a room. When: splitting regions during BSP generation. Why: Too close to a border leaves a part too small to contain a room.
- [rule] Cap room size by the cell size, so rooms never overlap or leave the map; use larger cells or merged cells for large rooms.
- [rule] Use only even numbers for room positions and sizes so corridors do not run side by side or hug room edges. When: Placing rooms and corridors on a tile grid. Why: Even coordinates keep parallel corridors and room edges separated, giving a tidier layout.
- [rule] Both grid dimensions must be odd for the odd-coordinate lattice maze carver to work. When: Carving a grid maze on an odd-coordinate lattice. Why: Carved cells sit on odd coordinates, so even dimensions break the lattice.
- [rule] Remove leftover three-cell L-shaped turns with a postprocessing pass, although such turns are seldom present. When: Finishing a perturbed path made of short straight segments. Why: Short segments can leave occasional sharp corners that a cleanup pass fixes.
- [rule] Avoid mixing many room types without restriction, since it yields odd and implausible layouts. When: Generating dungeon layouts from a broad set of room types. Why: Unrelated room styles combined together do not read as a coherent place.
- [rule] Keep wide tunnels rare, since too many width 2 or 3 tunnels turn the dungeon into swiss cheese. When: Choosing tunnel widths for a generated dungeon. Why: Wide tunnels remove too much wall, leaving a porous layout.
- [rule] Adjacent regions of the same type should skip generating their shared edge terrain, so the edge is not generated twice. When: when generating neighbouring regions of the same type. Why: avoids duplicate or conflicting edge terrain.
- [heuristic] Keep layout (rooms and connectivity), geometry (tiles, corridors, doors) and corridor algorithms in separate code, so each stage can be changed or swapped independently. When: Designing a room and corridor generator.
- [heuristic] Rooms-and-corridors dungeon layouts are not required in a roguelike, since they are only a low-value factor.
- [heuristic] Corridor and room shape determines how often a player can take a step toward a monster before engaging. When: generating rooms and corridors for melee combat. Why: Layout controls whether a charging approach is possible.
- [heuristic] Consider letting some rooms grow to hold many swarming monsters, like a town level.
- [procedure] 1) Fill the map with solid rock or split it into equal block cells of a chosen size. 2) Pick a random empty cell, or a block-aligned top-left corner whose blocks are free. 3) Place a room, mark its cells used and flag its edges for corridors. 4) Repeat until the target room count is reached, then seal the edge with permanent rock. When: Placing rooms on a grid of cells or blocks. Why: Occupancy marking prevents overlap and keeps placement orderly.
- [procedure] 1) Split the map in two. 2) Repeat on each new area until it reaches a minimum width, height, or area. Optionally split areas into even grids such as 3x1 or 3x3. When: generating rooms for a fantasy dungeon layout. Why: Repeated splitting with size limits yields rooms of controlled size.
- [procedure] 1) Project both rectangles onto the x axis and y axis. 2) They are neighbours when the overlap is positive on exactly one axis and zero on the other. When: testing whether two rectangles share an edge. Why: A shared edge means touching along one axis while overlapping along the other.
- [procedure] 1) Fill the area solid. 2) Carve a line from each gateway to the centre. When: painting a tunnel-style area. Why: Radial corridors connect every gateway through a shared centre.
- [procedure] 1) Draw walls on the area border. 2) Leave gateway cells open. When: painting a room-style area. Why: Border walls give a closed room whose only exits are the gateways.
- [procedure] 1) Fill the area solid. 2) Connect each gateway to the next one in a ring. When: painting a tunnel area that should link all its gateways in a loop. Why: Ring corridors give every gateway a route to every other gateway.
- [procedure] 1) Fill a rectangle with walls. 2) Split it recursively, choosing horizontal or vertical at random, until leaves are about room size. 3) Place a random-size room inside each leaf. 4) Join sister leaves with corridors. 5) Move up the tree and join sub-regions until the first two sub-dungeons connect. When: generating a basic dungeon with rooms and corridors. Why: Non-overlapping leaves guarantee that rooms never overlap while recursive joining connects the whole level.
- [procedure] 1) Join each leaf to its sister. 2) If facing walls line up, use a straight corridor. 3) Otherwise use a Z-shaped corridor. When: connecting sibling rooms in BSP generation. Why: Corridor shape depends on whether the facing walls align.
- [procedure] 1) Place 6 to 8 room points evenly around a circle, rotated by a random angle. 2) Assign each room a corner anchor that fills the circle. 3) Grow branches in up to three generations. 4) Link first-generation rooms into a loop, then connect each generation to its parents with straight or L-shaped paths, carving paths before rooms. When: Compact layouts with a built-in loop are wanted. Why: Starting from a loop avoids the detours and maze-like spacing of random-walk trees.
- [procedure] 1) Start with an empty 8x4 mini-map. 2) Give each x-direction row either three vertices or two non-adjacent vertices. 3) Sweep with 3x3 windows, then 2x4 windows. 4) Give any window still empty two extra vertices. 5) Collect all vertices into set A.
- [procedure] 1) Start at a cell and mark it visited. 2) Shuffle the four directions. 3) For each direction, if the neighbour two cells away is inside the border and unvisited, open the passage between them and recurse from that neighbour. 4) When no direction works, return. When: Carving a perfect maze on a grid.
- [procedure] 1) Split the map into nine non-overlapping areas. 2) Place one room at a random position and size inside each area and store the room list. 3) Carve corridors before rooms. 4) Shuffle the room list. 5) Link each room to the previous one with a corridor from a random point in each. When: Generating a simple classic-style room and corridor level. Why: Carving corridors first keeps them from cutting through rooms, and shuffling varies the connection order.
- [procedure] 1) Draw a straight line between two cells using a standard line-drawing algorithm. 2) Sample waypoints from it, skipping two or three cells each time. 3) Repeatedly nudge a random interior waypoint one cell in a random direction. 4) Accept the nudge only if no angle becomes too sharp and segment lengths stay within 2 to 5 steps. When: Making a gently winding path between two points for roads, rivers or corridors. Why: Small accepted nudges bend the line while angle and length limits prevent sharp or irregular turns.
- [procedure] 1) Connect each room to every later room in sequence. 2) Start corridors from the origin room's centre toward the destination's centre. 3) Place doorways only in outer walls, skipping inner walls. 4) If the corridor fails, place nothing. When: Joining rooms after placement in a room-and-corridor generator. Why: Sequential attempts build loops, and discarding failed corridors avoids half-built paths.
- [procedure] 1) Create two overlapping rectangles. 2) Use their union or intersection as the room's shape. 3) Define regions north, south, east, west and the intersection for content placement. When: Generating rooms with irregular but structured shapes. Why: Named regions give placement logic a consistent frame.
- [procedure] 1) Pick two random rectangles. 2) If one encloses the other, the result is a plain rectangle. 3) If they are identical and mirrored at 45 degrees, the result is a cross-shaped room. 4) Bias symmetry so cross rooms appear more often. When: Generating overlapping rectangular rooms. Why: Rectangle relations yield distinct shapes from a simple rule.
- [procedure] 1) Pick one origin. 2) Cast rays of random length outward. 3) Join the ray endpoints to form a curved-edged room. 4) Place lakes first and draw them with starbursts. When: Generating organic, curved-edged rooms or lakes. Why: Random ray lengths produce irregular outlines without manual shaping.
- [procedure] 1) Recursively pick templates, including pools. 2) Reject the result unless all floor and pool squares connect. When: Generating fractal-shaped rooms. Why: Recursive templates can create disconnected pockets, which the check removes.
- [procedure] 1) Sort room types from largest to smallest. 2) Place the hardest-to-fit rooms first. 3) Place smaller rooms into the remaining space. When: Filling a level with room types of varying size. Why: Large rooms need open space that smaller rooms would otherwise consume.
- [procedure] 1) Place non-overlapping rooms by trying a fixed number of random positions, discarding collisions. 2) Fill each leftover solid area with a maze that carves only into rock. 3) Find connectors, solid tiles adjacent to two regions. 4) Build a spanning tree by repeatedly opening a random connector to the main region. 5) Keep redundant connectors with a small chance for loops. 6) Remove dead ends. When: when generating a dungeon with rooms, corridors and loops that is fast enough to build on level entry. Why: produces a fully connected layout with varied passages.
- [metric] Split positions between 0.45 and 0.55 of the way across produce similar parts, while positions between 0.1 and 0.9 produce varied parts. When: tuning the uniformity of room sizes in BSP generation. Why: Narrow split ranges keep sibling regions close in size, wide ranges spread them out.
- [metric] Iterations equal the number of waypoints times a caller-supplied factor; for roads of length 50, factors of 10 to 30 give decent results. When: Running the waypoint perturbation method on a path of about 50 cells. Why: More iterations let the path bend further from the straight line.
- [tradeoff] Dungeons suit level-based games since they are easy to generate and have clearly defined levels, while caves, wilderness or cities can complement them.
- [tradeoff] Straight or L-shaped carving is simple but overwrites walls and can leave rooms without doors; pathfinding routes around walls and avoids this at the cost of more complex code. When: Choosing how to link rooms in generated layouts. Why: Paths overwrite wall tiles that door placement depends on.
- [tradeoff] Orthogonal grid corridors give plain paths that suit projects needing about 8 to 14 rooms with a main loop, but they may look poor and need improvement.
- [tradeoff] The regular grid makes layouts fast and easy to theme and to swap corridor styles, but gives a regular feel that may not suit caves.
- [pitfall] A linear route designed on an abstract graph becomes hard to see once the full dungeon is generated and painted. When: reviewing an abstract layout before painting. Why: Walls and tiles obscure the graph structure that defined the route.
- [pitfall] A layout method can yield an area distribution that does not look good, so the output needs checking. When: generating abstract dungeon layouts. Why: Area shapes and sizes depend on the method and its parameters.
- [pitfall] Rooms can look too evenly spaced after painting, so skipping some columns or rows adds variety but requires a corridor to the centre to cover the offset. When: painting room-style areas on a grid. Why: Skipped rows or columns create offsets that must be bridged to keep rooms connected.
- [pitfall] Stopping a corridor when it hits an existing one forms a T-junction and keeps connectivity, but crossings are only partly solved by this simple hack. When: Drawing corridors that may cross earlier corridors. Why: The stop rule avoids crossings but is an approximation rather than a full solution.
- [pitfall] Passages tend to be annoyingly windy, and straightening them can push corridors to the dungeon edge. When: when tuning maze or corridor shape. Why: straighter paths change how corridors route around rooms.
- [pitfall] Odd-aligned room and maze boundaries give a level an artificially grid-aligned look. When: when aligning rooms and mazes on a grid. Why: regular alignment is visible to players.
- [fact] Dungeons of rectangular rooms joined by passages were the original roguelike map form and are the oldest class of roguelike maps.
- [fact] Line-of-sight and range conditions for automatic target-mode exit depend on the map layout.
- [fact] Simpler layouts are easier for players to read and for designers to edit, so room count and map size should be kept under control. When: Choosing room count and map size for circle layouts. Why: Readability and editability suffer as layouts grow.
- [fact] Keeping the room list helps later stages place items and monsters and compute field of vision. When: Building a room and corridor generator. Why: The stored room structure gives downstream systems a ready reference.
- [fact] Layout forms include huge rooms, natural caverns, two- or three-wide corridors, long hallways, pillared large rooms, and large doors.
- [fact] Tile-based maze and map generation is the established baseline for roguelike levels.
- [fact] Corridors can cut through single-width walls but not double-width walls, so vault designs must account for this limit. When: Designing vaults or walls that corridors must cross. Why: The carving routine treats thick walls as impassable to corridors.
- [fact] An area spell sized for standard corridors breaks when a dungeon uses realistically wider corridors. When: Generating dungeons with varied corridor sizes. Why: Fixed area sizes assume a corridor width the map may not have.

## procedural generation
- [model] Four strategies find interesting procedural content: simulation, AI direction, human computing and intuitive tuning. They can be blended. When: Choosing how to make generated content interesting. Why: Each strategy finds interest in a different source, and combining them covers more.
- [model] Five decision axes describe a procedural generator: online versus offline, necessary versus optional, random seed versus parameter values, stochastic versus deterministic, and constructive versus generate-and-test. When: when specifying or comparing a generator's design before implementation. Why: the axes describe requirements of an algorithm rather than what counts as procedural.
- [model] Runtime level generation builds each level at play time from random or pseudo-random steps. Two-dimensional generation is well covered by known algorithms, while three-dimensional generation is less developed.
- [model] Procedural frameworks let users create content without deep technical knowledge, by offering a template that covers all possible outputs and steering users toward high-quality results. When: Designing tools for users who are not programmers. Why: Templates constrain output space so that user choices stay within quality bounds.
- [definition] In roguelikes, item placement and appearance are random and monster appearance is fixed while their placement is random; fixed content such as vaults or puzzles counts against randomness.
- [definition] In an abstract dungeon, an area is a rectangle or polygon defining part of the map, a cell is one tile, and a gateway is a cell connecting two areas.
- [definition] In map generation, a cell is a value at one map point, a map is a 2D array of cells, a predicate tests a location, and a brush modifies one or more cells.
- [definition] Procedural content is generation built for gameplay, where the player supplies the meaning.
- [definition] Complex generation problems include routing problems like the travelling salesman problem, and ordering rooms and corridors, which lack clean solutions.
- [definition] An expert system can act as a generator, adding rule-following features, or as a constrainer, limiting what the generator may produce.
- [definition] Ontogenetic generation reproduces the output of a physical process while skipping its intermediate steps.
- [definition] Teleological generation simulates the physical processes that lead to the desired output.
- [definition] A procedural game presents biased randomness whose underlying rules can be discovered, and that discovery is part of play.
- [mechanism] Permadeath and per-session regeneration of most of the world show fresh generated content each game, increasing replay and softening the frustration of starting over.
- [mechanism] Randomized dungeon layout, enemies and items make each run differ, and players start to recognize recurring patterns as themes. When: when base mechanics are sound. Why: randomness creates new situations each run.
- [mechanism] Procedural generation, randomness and permadeath keep a game challenging even when a player knows all its rules. When: Designing roguelike or generated games. Why: Unpredictable content keeps challenge alive after rules are known.
- [behavior] Roguelikes show that procedural content can avoid the repetitive and predictable failings often attributed to it. When: when generated content is built around a roguelike loop. Why: varied runs keep play interesting.
- [rule] Use layered simple rules, such as height, moisture and temperature producing biomes from fractal subdivision, for depth problems; use search, constraints or fallbacks for complex problems. Why: Combining simple layers yields varied results.
- [rule] A good procedurally generated name must be pronounceable and must have an adequate feel for its setting.
- [rule] Use obviously artificial styles for generated content meant to look generated, and avoid high-fidelity imitation where its origin is likely to be revealed. When: when choosing a visual or audio style for generated content. Why: Revealed hidden algorithmic origin can make players feel betrayed.
- [rule] Use source code and version-controlled builds as references over incomplete documentation when modding. When: Modding a game with incomplete documentation. Why: Source code is more accurate than partial documentation.
- [rule] Plan the testing budget for generators before shipping, not after. When: when preparing a procedural generator for release. Why: late testing leaves less time to fix generator failures.
- [heuristic] Use human choice to filter generated output when taste matters or quality is hard to specify in rules; selection steers results toward interesting outputs without a formal quality definition. When: Generated content is presented to players or designers for selection, or output quality is hard to specify in rules. Why: Human judgement supplies taste that pure randomness lacks.
- [heuristic] The two-term split of generation approaches is more useful than a long taxonomy of many procedural categories. When: when classifying procedural generation methods. Why: two terms clarify the core choice better than many minor categories.
- [heuristic] Check whether a procedural technique has already been tried in a given space before adopting it. When: when choosing a procedural technique. Why: prior work reveals proven and unproven options.
- [heuristic] Do not use procedural generation design axes as a rigid taxonomy for classifying games. When: when classifying games by their generation methods. Why: the axes describe decisions of a given algorithm, not fixed categories.
- [heuristic] Commit to a definition of procedural content only as far as it helps build a particular algorithm. When: when defining procedural content for a project. Why: narrow definitions can obstruct useful design choices.
- [heuristic] Feature difficulty depends on the surrounding code architecture, so a generic list of hard features is not a universal estimate. When: Estimating how hard a feature is to implement. Why: The same feature can be easy in one codebase and hard in another.
- [heuristic] Share development stories and logs alongside code, since they teach why a method works better than final code alone. When: when documenting or teaching procedural techniques. Why: Final code does not explain the reasoning behind the method.
- [procedure] 1) Run automated bots through a dungeon generator to surface crashes and hangs. 2) Sample generated levels statistically to estimate how much of the space has been covered. When: when testing a dungeon generator. Why: bots catch hard failures while sampling estimates coverage of an infinite space.
- [tradeoff] Producing a result directly is usually cheaper, while simulating the process that creates it is more faithful. When: when deciding how to generate content. Why: direct output saves computation, simulation preserves the physical causes.
- [tradeoff] Low-fidelity generated content is obviously artificial and avoids the unease, while high-fidelity content must match genre conventions to pass as human-made but is expensive to build. When: when deciding how closely generated content should imitate human work.
- [tradeoff] Seeded on-demand generation avoids storing huge worlds but struggles with long connected structures such as rivers, and changing the algorithm changes the entire world, breaking saved worlds. When: Choosing between seeded on-demand generation and stored level data. Why: Subdivision cannot easily model features that depend on neighbouring regions, and algorithm changes alter every generated output.
- [pitfall] Random layouts can frustrate players who expect a level to stay the same when they return. When: Levels are regenerated on each visit. Why: Players expect continuity of places they have explored.
- [pitfall] Procedural content is often criticised as repetitive, predictable, exploitable and inferior to handmade design. When: when evaluating generated content. Why: generated content lacks the authored variety of handmade design.
- [pitfall] Analysis-based approaches built on player data are not straightforward to apply, and they matter most for multiplayer maps. When: Relying on player data to drive generation or design. Why: Data interpretation is difficult, and multiplayer maps yield more varied player behaviour to learn from.
- [pitfall] Building messages in code makes programmers handle grammar, which is better left to translators.
- [pitfall] Tuning a dynamic system to behave well across many possible states is hard, and dynamic systems face the same contingency problems as procedural content generation. When: Designing any system whose outcomes depend on many interacting states. Why: The number of reachable states grows quickly, so untested combinations will appear in play.
- [pitfall] Frequent changes to a game's core rules hide which design features have endured, so such games are weak references for lasting design. When: choosing reference games to study. Why: Core rule churn makes it unclear which features were actually successful.
- [fact] Most in-game content in roguelikes, such as items, monsters and world characteristics, is generated by algorithms driven by a random number generator.
- [fact] Random quests, random plot, random overworld, and cellular automata dungeons are named as hard generation problems and are harder than their theory suggests. When: Planning procedural content in a roguelike. Why: They require coherence across many generated parts.
- [fact] A single map can combine several generation types, such as room generation in one zone and cave generation in another, joined by pathfinding tunnels. When: Designing a level from multiple generators. Why: Zones let different generation styles coexist on one level.
- [fact] Any attempt to create something procedurally is guided by either the ontogenetic or the teleological approach, though the two can be combined.
- [fact] Procedural generation is a continuum running from procedural graphics and animation through maze generation to world building, rather than a split between content and effects. Why: the earlier split between content and effects was too narrow.
- [fact] Frequent procedural methods include heightmaps for terrain, grid-based labyrinth creation and random loot drops.
- [fact] Each procedural generator design axis is a continuum rather than a binary switch.
- [fact] Procedural generation is distinct from sandbox play and emergence; these three properties are separate but often coincide in the same game.
- [fact] Infinite worlds, random maps, random loot, AI and emergence each fail as a definition of procedural games on some examples.
- [fact] A formalised game design vocabulary could in principle support automated generation of rule variants and game spaces. Why: Speculative idea, not yet demonstrated.
- [fact] Floor layouts, room templates and terrain features can be stored as text data so new room types or maps are added without recompiling.
- [fact] Procedural content creates webs of interacting cases, so simple test cases cannot cover it.
- [fact] The space of procedural content is effectively infinite, so full coverage is impossible and coverage must be judged statistically before release.
- [fact] Procedural generation of art and levels is expected to first support existing artists and level designers rather than replace them.

## pacing and level progression
- [model] Hard generation problems split into two kinds: depth, where many simple building blocks combine into rich output, and complexity, where no clean solution exists or costs explode.
- [definition] Dungeon persistence describes whether a level keeps its state when the player leaves and returns; the four models are non-persistent, persistent, mostly persistent, and one-way.
- [mechanism] Sliding a small window of upgrade options forward through an ordered list as the run deepens yields many builds without overwhelming players or exposing high-level options too early. When: Generating upgrade offers or many total options over a procedurally generated run where each decision should stay small. Why: Players reason clearly over a few visible options; offering everything at once breaks rational decisions, and timing the window to depth keeps offers matched to current power.
- [mechanism] Connecting levels by stairs creates progressive difficulty, since each level is more dangerous than the last.
- [mechanism] Food placement sets the pace of descent, because food must be found by delving deeper. When: Placing food in a dungeon generator. Why: Players must go deeper to find food, so food location drives progression speed.
- [mechanism] A non-persistent level is regenerated each time the player re-enters it through the same entry point, so no level state needs to be stored.
- [mechanism] In a one-way level the player cannot return once they leave, which removes the persistence question and can set mood.
- [mechanism] One-way levels create choices, such as skipping half a level to escape a dangerous monster, because leaving is permanent.
- [mechanism] Dynamic systems create unpredictable states inside a fixed map, cutting scripting effort because developers set high-level goals instead of scripting each encounter. When: Scripting every encounter is too costly and high-level goals are enough to drive play. Why: Dynamic AI reacts to world state, so the same authored space yields varied outcomes.
- [mechanism] Re-entering a staircase returns the previously generated level rather than a fresh one, so repeatedly taking stairs cannot reroll a level for a better layout. When: Players can use stairs to regenerate levels. Why: Persisting levels per staircase removes the rerolling advantage of stair scumming.
- [rule] Save points must be placed away from critical rooms such as bosses so players cannot save just before danger. When: Generating layout for save points in a dungeon. Why: Saving right before a boss removes risk from the challenge.
- [rule] Level contents should be fixed or seeded when first generated, otherwise reloads reveal new layouts.
- [rule] Give each floor themes that overlap, such as depth, rock type and hazard, so one clue does not reveal the whole floor. When: designing dungeon floors.
- [rule] Make generated assets clearly disposable so that losing them does not feel like losing the player's identity. When: Designing procedurally generated items or characters the player owns. Why: Easy replacement keeps losses from feeling like personal loss.
- [heuristic] Temples or shrines placed inside large dungeon complexes provide respawn points and add variety. When: Designing large dungeon complexes. Why: Respawn points reduce long backtracking after death.
- [heuristic] Place pitfalls and rewards as stages along a generated route, with open areas for roaming between them. When: Procedurally generated routes.
- [heuristic] Horror in a roguelike can be built by making fights deadly, revealing little, showing monsters only as glimpses, and keeping danger constant so the player feels helpless and paranoid. When: designing a roguelike meant to feel like true horror. Why: Uncertainty and helplessness make threats feel larger than their stats, so the player's imagination supplies the dread.
- [heuristic] Measure how much of a level the player must or wants to explore before finishing it, to turn fun into a measurable quantity.
- [heuristic] A stealth-based reward works only if the generated level offers routes that let a player reach an unaware monster unseen. When: generating levels for stealth-triggered abilities.
- [heuristic] A dungeon director can pace monster arrivals over time, provided the effect is bounded so the level does not empty or flood. When: Generating dungeons or levels that need controlled tension over time. Why: Pacing control is amenable to procedural management, and bounds prevent runaway population changes.
- [heuristic] Give each generated run a visible end, such as a final floor or depth limit, so every mid-run resource choice has a clear purpose. When: Designing roguelike or run-based dungeon generation. Why: A known endpoint lets players judge the value of resources against it.
- [heuristic] The deepest levels should be the most open, with the final enemy in a central lair such as a throne or gate. When: Laying out the final levels of a dungeon. Why: A single central destination gives the finale a clear spatial focus.
- [heuristic] A procedural generator's rules should be tested by playing the generated output, not only reviewed on paper, to catch degenerate strategies. When: When designing a dungeon or level generator. Why: Paper review cannot reveal exploits that emerge from play.
- [heuristic] Procedurally generated roguelikes can keep harsh early encounters, because permadeath and generation make learning the lesson cheap. When: When a roguelike uses permadeath and procedural generation. Why: Repeated runs make a harsh early lesson inexpensive to relearn.
- [heuristic] Treat the map as the quest structure and check its connectivity rather than scripting each path, so a generator can place gates whose requirements are met by later finds. When: Generating maps where progression depends on gates and keys. Why: Structural checks scale to procedural content better than hand-scripted paths.
- [heuristic] Discard or regenerate levels when content is effectively infinite and cheap to create. When: when generated content is cheap to produce. Why: regeneration clears bad layouts at low cost.
- [procedure] 1) Keep terrain fixed between visits. 2) Set a rate for how often wandering monsters repopulate the level. 3) Perform the repopulation on each return.
- [procedure] 1) Select a category first, such as gold, potions, equipment or boosts. 2) Then select a subtype within that category. Why: Two stages keep each category's table small and easy to tune.
- [procedure] 1) Track whether the run still holds the items needed to finish. 2) Detect when they are lost beyond recovery. 3) Prevent or flag that state before the player is stuck. When: Procedurally generated runs with consumable or key items. Why: Catching an unwinnable state early avoids a stuck run that feels unfair.
- [procedure] 1) Try the largest and hardest-to-place room types first. 2) Place the first room that fits. 3) Use its type to set the level theme that limits later room, tunnel and description choices. When: Generating a level from a set of room types with varied placement difficulty. Why: Placing hard rooms first secures the most constrained choice, and the theme keeps the level's architecture consistent.
- [tradeoff] Non-persistent levels avoid storage and size problems but make it easy for players to farm earlier levels for experience and treasure.
- [tradeoff] Discarding levels encourages stair scumming and avoids item loss, while persistent levels risk losing stashed items but give the player more choice. When: when choosing how long levels persist. Why: persistence trades item safety against freedom to plan.
- [tradeoff] Letting two downward stairs lead to different levels allows a dangerous level to be bypassed. When: when a level has a dangerous layout. Why: a choice of destinations gives the player a way around threats.
- [pitfall] A placement loop that retries and aborts when a connection fails can run forever unless it has a retry limit. When: placing paths or rivers that must connect. Why: Naive retries have no guaranteed end.
- [fact] Teleport and portal spells depend on the dungeon's level layout and connections.
- [fact] Episode-based plots give a natural way to split a run into stages within a generated dungeon.
- [fact] In many roguelikes, monster and item generation depends only on depth.

## monster and inhabitant placement
