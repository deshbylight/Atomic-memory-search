# programming

## spreadsheet formulas
- [definition] A spreadsheet formula starts with an equals sign and can combine numbers, the operators +, -, *, and /, and cell references.
- [definition] A cell reference combines a column letter and a row number, and a formula that uses it takes the value currently stored in that cell.
- [definition] A relative reference stores its position relative to the formula's cell, so copying the formula shifts the referenced cell by the same offset.
- [definition] An absolute reference places dollar signs before the row and column, like $C$2, so it stays fixed when the formula is copied or filled. When: Applying one shared constant to a whole column of formulas.
- [definition] Conditional formatting styles only the cells that satisfy a chosen rule, using a fill or a text style.
- [definition] Freezing pins chosen top rows or left columns in place so they stay visible while the rest of the sheet scrolls.
- [definition] A tiebreaker sort column orders rows only where all earlier sort criteria are equal.
- [definition] The mean equals the total of all values divided by their count.
- [definition] MEDIAN returns the middle value, MODE the most frequent value, MAX and MIN the largest and smallest values, and STDEV the standard deviation.
- [definition] COUNTIF tallies the matching cells within a range for a given criterion, while SUMIF totals their values using the same parameters.
- [definition] IF(condition, value_if_true, value_if_false) returns one of two results depending on whether a Boolean test holds.
- [definition] FLOOR(number, significance) rounds a number down to the nearest multiple of the significance value.
- [definition] A spreadsheet function call is written as its name, an open parenthesis, its parameters if any, and a closing parenthesis.
- [definition] SUM() accepts any number of parameters, each a single cell or a cell range, and returns their total.
- [definition] A range is written as two corner cells joined by a colon and covers every cell in the rectangle between them.
- [definition] MATCH(key, range, type) returns the position of a key within a single row or column, counting from 1 at the top or left.
- [definition] MATCH's third argument sets the search mode: 1 assumes ascending order and returns the closest value not exceeding the key, -1 assumes descending order, and 0 requires an exact match.
- [definition] INDEX(range, row, column) returns the cell content at the given row and column inside the range.
- [definition] INDIRECT builds a cell reference from a text string, so a random number joined into the string can select which cell's content is returned.
- [definition] A named range is a name assigned to a single cell or a range of cells, which formulas can use in place of cell addresses.
- [definition] COUNTA(range) returns a tally of non-empty entries within the given span.
- [definition] COUNTBLANK(range) returns the number of empty cells in the range.
- [definition] ISBLANK(cell) returns TRUE if the cell is empty and FALSE if it holds anything, and works as the condition inside IF().
- [definition] SPARKLINE() places a small chart inside a single cell, letting many rows each show a trend without large charts covering the sheet.
- [definition] A solver add-on takes input cells, a target output cell and a desired value, then searches for input values that reach the target or come as close as possible.
- [definition] BOOLEAN has values TRUE and FALSE, with conjunction &, disjunction OR and negation ~; comparisons yield BOOLEAN results that can be assigned or used as operands.
- [definition] CAP(ch) returns the capital letter for a lower-case letter and leaves a capital letter unchanged.
- [mechanism] TODAY, NOW, RAND and RANDBETWEEN keep their values until the sheet changes or a recalculation is forced, since any edit triggers recalculation of random-based cells.
- [mechanism] Inserting or deleting rows and columns, and cutting and pasting cells, automatically updates every formula that refers to the affected cells.
- [mechanism] When a formula is copied or filled, its cell references shift to match each new position, so every copy refers to its own row or column.
- [mechanism] A formula that references other cells updates its result automatically whenever a referenced value changes.
- [mechanism] When computing a cell, the spreadsheet first evaluates each parameter, then applies the function to those computed values.
- [mechanism] Adding a fraction of a day to a date-time value shifts it by that share of a day, so adding 0.25 moves it forward six hours.
- [mechanism] Dates behave as numbers: subtracting two dates gives the days between them, and adding a number gives the date that many days later.
- [mechanism] Each lookup costs CPU, and the first use of a service pauses while it is found, so caching the result avoids repeated delays.
- [rule] Avoid connected-wildcard searches on large databases: two connected clauses take O(n²) time, and more connected clauses cost considerably more than independent ones. When: When the rule database is large, or clauses share wildcards. Why: Each candidate from the first clause must be tried against the second.
- [rule] When results look wrong, read the true value of the selected cell in the formula bar instead of trusting the displayed number.
- [rule] Resize a row or column by dragging its heading border, or enter an exact size from the heading's right-click menu.
- [rule] Shade computed subtotal columns in a distinct color so they are not typed over by hand.
- [rule] Reference a whole column, such as C:C, in statistics formulas so that new rows are included without editing the formula; text headers are skipped. When: the column has a header row and its data keeps growing.
- [rule] Give a bare value for an exact match, and write a comparison as one quoted criterion such as '>=14' with the operator inside the quotes.
- [rule] Set MATCH's third argument to 0 for unsorted data so it returns only exact matches. When: the lookup list is unsorted. Why: the approximate modes assume sorted data.
- [rule] Use MATCH to find a key's position when it sits in an arbitrary place, such as an item in a loot table.
- [rule] Place summary cells above a task list that count incomplete tasks and overdue tasks.
- [rule] Anchor matrix references with absolute row or column markers and leave vector references relative, so one formula fills correctly down and across.
- [heuristic] Write derived column formulas that reference inputs in the same row, so each row computes its result independently. When: building calculated columns from input columns.
- [heuristic] Freeze header rows and the name column in any sheet larger than one screen, so each value stays labeled while you scroll. When: the sheet has more rows or columns than fit on screen.
- [heuristic] Rotate long column headings so they remain readable and a wide sheet stays compact. When: column headings are long and the sheet is wide.
- [heuristic] Text aligns left and numbers align right by default; centering column headings often makes them easier to read.
- [heuristic] Merge cells mainly for presentation, such as a category heading spanning a group of column headings, rather than for storing data.
- [heuristic] Use IF to flag rows that meet a criterion, or to assign values to every item that has a given attribute. When: Setting stats for all entities sharing an affiliation, or marking rows matching a test.
- [heuristic] For simple done versus not-done tallies, blank checks are easier to use than COUNTIF.
- [heuristic] Date formulas suit organizing personal work, such as deadlines and countdowns.
- [procedure] 1) Compare the deadline cell with TODAY(). 2) Inside IF(), show a blank if the task is complete, OVERDUE if incomplete and deadline earlier than today. 3) Otherwise show days remaining until the deadline. When: tracking deadlines in a task list or marking items whose deadline has passed.
- [procedure] 1) Select the formula cell and the cells below or beside it. 2) Press Fill Down (Ctrl+D) or Fill Right (Ctrl+R) to copy the formula across the range. When: copying one formula across a row or column.
- [procedure] To fill a formula across a rectangle, select the whole area, apply Fill Right, then apply Fill Down.
- [procedure] To verify a filled formula, select any cell in the range and read the formula shown in the formula bar.
- [procedure] 1) Enter a starting value in the first row. 2) In each following row, add a fixed increment to the cell directly above. 3) Repeat down the column. When: building a column that grows by a constant step.
- [procedure] 1) Place the shared constant in a fixed cell. 2) Reference it with dollar signs in the formula. 3) Fill Down the formula. Changing the constant then updates every row. - [procedure] 1) Select the cells. 2) Click Merge and choose Merge All. 3) To reverse it, select the merged cell and choose Unmerge.

- [procedure] 1) Give the data range as the first argument. 2) Give options as the second argument inside curly braces. 3) Write each option as its name, a comma, then its value. 4) Separate multiple options with semicolons. Chart type options include line and column.
- [procedure] 1) Copy a block of cells. 2) Right-click the target and choose Paste Special. 3) Choose Paste Transpose. The block's rows and columns swap, so a 3 by 4 block becomes 4 by 3, keeping its data and formulas. When: chart data is laid out sideways.
- [procedure] 1) Highlight a source cell. 2) Click the format painter button. 3) Click a target cell, a row or column heading, or drag across a range to apply its formatting.
- [procedure] 1) Select an empty, unformatted cell. 2) Click the format painter. 3) Click the top-left corner of the sheet to strip special formatting from the whole sheet.
- [procedure] 1) Loop over every element of the array. 2) For each record, test the conditions on its fields. 3) Increment a counter when all conditions hold.
- [metric] A datum match stores an identifier with minimum and maximum values; equality is a zero-width range, and one-sided tests use an infinite bound.
- [metric] Numeric cells not matching a value equal COUNT over the range minus COUNTIF for that value over the same range.
- [tradeoff] Names make formulas read clearly at a glance, while cell addresses show exactly where the referenced data lives. When: choosing how formulas reference data.
- [tradeoff] Spreadsheet matrix work keeps data in one tool and avoids exporting, but dedicated matrix software suits large or unwieldy work better. When: choosing where to compute matrix operations. Why: Keeping data in place saves transfers, while large matrices strain spreadsheets.
- [pitfall] In some spreadsheet apps, once a rule matches, its formatting applies and later rules are skipped, so an earlier match blocks later rules and rule order decides the visible formatting. When: rules are applied with first-match-only behavior.
- [pitfall] If the test value falls outside the mapped set of daughters, the lookup finds no daughter, so the node must handle that case explicitly.
- [pitfall] In a recursive odds grid, a formula that points to the wrong cell gives wrong results silently, so check several cells against hand-calculated base cases. When: Building a recursive spreadsheet table for game odds. Why: Mis-referenced cells propagate errors through every dependent cell.
- [pitfall] Resizing a row or column alters every cell in it, making it a clumsy way to adjust a single cell.
- [pitfall] A merged block keeps its value only in its top-left cell, so referencing any other cell in the block returns no value.
- [pitfall] Including header rows in a sort risks pushing headings into the data rows.
- [pitfall] Dates and times are stored as numbers, so SUM or AVERAGE over them gives meaningless results, although COUNT still tallies them.
- [pitfall] SPARKLINE syntax is harder to write than basic chart tools because its many options make it versatile but intricate.
- [pitfall] Pasting only formatting is a separate action from pasting the full block, so confirm which paste option you selected.
- [pitfall] The ArrayFormula function is specific to one spreadsheet app; other apps use curly braces, so exported array formulas may need manual fixing.
- [pitfall] Spreadsheet matrix work is harder to build and check than ordinary formulas, so expect more effort.
- [fact] An AND match succeeds only when both sub-matches succeed, while a NOT match tests its sub-match with a fresh bindings list and so records nothing.
- [fact] A computer can simulate a dN for nearly any N, so virtual dice are not limited by physical manufacturing.
- [fact] Fill Up and Fill Left have no keyboard shortcuts; instead, drag the small square at the bottom-right of the selection in any direction.
- [fact] Freezing rows and freezing columns are separate choices, so you can freeze headers, a name column, or both.
- [fact] AVERAGE accepts any mix of cells and ranges and skips blanks, text and other non-numeric entries.
- [fact] Summing a column of IF results that return 1 or 0 gives the number of rows that meet the condition.
- [fact] Comparing a cell to an empty pair of quotation marks returns true when that cell is blank.
- [fact] AND(...) returns true only when all its parameters are true, so a lower and upper bound check combined inside IF tests a range.
- [fact] CEILING rounds a number up to the next multiple of a significance value, and MROUND rounds it to the nearest multiple.
- [fact] Functions can stand alone or combine with numbers and cell references in arithmetic, and a parameter can itself be another function.
- [fact] Omitting one side of a range selects an entire row or column.
- [fact] Forced recalculation shortcuts differ between spreadsheet programs, so search the program's help for recalculate to find the right command.
- [fact] VLOOKUP searches only the leftmost column of its table, and its column index counts from the left, with 1 meaning the leftmost column.
- [fact] CONCAT joins its inputs as text, so it can insert separator words between parts of a name.
- [fact] INDEX and MATCH together look up values at any position, not only in the leftmost column.
- [fact] The & operator joins text strings in all major spreadsheet programs without needing a special function.
- [fact] A named range is an absolute reference, so copying, pasting, or filling formulas does not change which cells it points to.
- [fact] HOUR returns 0 to 23, while MINUTE and SECOND each return 0 to 59.
- [fact] In a popular browser-based spreadsheet, Ctrl+R forces a recalculation.
- [fact] A spreadsheet can be configured to refresh each minute or each hour, though not each second or never.
- [fact] Painting a selected group of cells applies the group's formatting as one unit rather than cell by cell.

## physics simulation
- [model] Tires can be massless raycasts pointing down from each wheel well, not colliding wheels, so suspension forces come from ray hits on a rigidbody body.
- [model] Each tire keeps its own velocity and two friction values, sideways and forward, that act against that velocity. All vehicle motion comes from the tires.
- [model] In active ragdoll control, the player's inputs act through internal springs that change size like muscles, instead of applying external forces to the object.
- [model] A full physics simulation gives every object properties such as force, velocity, shape, gravity, friction and drag, so gameplay can emerge from their interaction. When: when building a physics-based game.
- [model] Simulated space has two parts: collision detection and response between the avatar and objects, and object placement and spacing relative to the avatar's speed.
- [model] Physical properties behind polish perceptions include mass, velocity, momentum, friction, gravity, shape, elasticity and plasticity.
- [definition] A collider makes an object interact physically as a simple shape, such as a box, regardless of its visible art.
- [definition] Game feel fakes Newtonian physics: players infer an object's properties from how it moves and interacts with other things.
- [definition] Ragdoll physics produces lifelike, unscripted movement for characters in real time, with limbs reacting to forces without hand-made animation.
- [definition] Simulated space is a physical world in which the avatar collides with and responds to objects, and the player perceives that world directly.
- [definition] Interaction with a unique physical reality is the fifth experience: players assemble a self-contained physical universe with designer-created laws from how objects respond.
- [mechanism] Drag slows a character every frame, capping top speed without an explicit clip check. When: Physics engines that apply drag.

## game loop
- [model] Each pluggable polling task holds a task code, stored value and last-updated frame; it refreshes only when stale versus the current frame, using one caching rule for all tasks.
- [model] Schedulers can run as behaviours inside other schedulers, forming a tree that divides time from the whole game down to individual character subtasks. Why: Each character's AI can be upgraded without unbalancing the rest of the game.
- [model] Game time machinery uses three patterns: a Game Loop that drives the world's clock, Update Methods that let objects respond to each tick, and Double Buffer that makes sequential updates look simultaneous.
- [model] Game loop ownership has three options: use the platform's event loop, use an engine's loop, or write your own loop.
- [model] The Update Method simulates independent objects by giving each an update() that advances it one frame; the game loop calls update() on every object once per frame.
- [definition] Besides processing each frame, the game loop must decouple progression from input and processor speed so the world advances at a consistent rate across hardware.
- [definition] Fixed time steps advance the world by one unit per update; variable time steps pass elapsed time into update(), so each frame simulates the previous frame's duration.
- [definition] The update time step is the fixed granularity at which the game is simulated, which is separate from the visible frame rate.
- [definition] A game loop is a continuously running cycle that processes input without blocking, advances the game state, renders the result, and tracks time.
- [definition] One cycle of the game loop is called a tick or a frame, and each cycle advances the game state by some amount.
- [mechanism] Without timing control, speed follows hardware and scene cost: fast machines blur, slow ones crawl, heavy AI or physics slows; tuning work to one PC shifts pace elsewhere. Why: Frame work sets speed directly, so each frame takes as long as its work and the machine sets the pace.
- [mechanism] When objects update sequentially and share state, update order silently changes behavior, since each reads whatever value was last written, such as a shared flag or previous frame position. When: components or actors read shared state written by others in the same frame or pass. Why: Reading and writing the same state within one pass makes results depend on update order, breaking the appearance of simultaneity.
- [mechanism] A pending transition at level zero is handled at this level, a positive level exits the current state and reduces the level, and a negative level passes to the parent's downward routine. When: A transition returned from a state update.
- [mechanism] A manual scheduler relies on each behaviour returning control after a short bout of processing, so no thread housekeeping is needed.
- [mechanism] Storing polling tasks in a hash table keyed by task code lets a request be served by looking up the task and returning its cached value.
- [mechanism] Digital systems run calculations behind the scenes that tabletop players would perform with dice, so the program produces random outcomes and results without the player doing the math. When: Role-playing combat resolution. Why: The program can run more calculations faster than a person with dice.
- [mechanism] A fixed-step loop cannot skip work to catch up, so a frame that overruns its time budget makes the whole game run slower.
- [mechanism] Fixed update with variable rendering keeps simulation at a fixed step and skips rendering frames to catch up, so it does not fall behind.
- [rule] Choose a fixed update step small enough for high-end hardware, yet longer than one update takes on the slowest supported hardware so low-end machines keep up. Why: A step shorter than the update cost means the game can never catch up with real time.
- [rule] Compile justification tracing out of shipped builds to avoid its memory overhead. When: Tracing is used during development but not needed by players. Why: Full trails can use substantial memory.
- [rule] The stability method needs a frame counter that increments once per tree call; if the tree is not run every frame, advance the counter each time it is called. When: When implementing stable random decisions.
- [rule] Every schedulable item exposes one run method that accepts a time value, and schedulers implement the same interface so they can be composed. Why: Shared interface lets schedulers nest inside each other.
- [rule] Route the polling that an event-based design still needs through a dedicated polling station, which gains speed and easier debugging. Why: some polling is usually needed to avoid awkward workarounds.
- [rule] Run the flush every frame, even when no new signals arrive, so cached notifications are dispatched on time. Why: cached notifications would otherwise be delivered late.
- [rule] In a browser, drive the game loop with requestAnimationFrame, letting the browser call your code back each frame. When: web browser target. Why: The browser's event loop runs the program, so the game must hook into it.
- [rule] Pass the normalized lag fraction to rendering instead of raw lag, so the renderer can ignore the update rate.

## memory layout and packing
- [model] Arrays and records are random-access structures for primary store, while sequences serve secondary stores such as disks and tapes, since tapes and each disk track allow only sequential access.
- [model] In the memory hierarchy, registers hold the data a CPU works on directly, RAM is the large slower store, and the cache sits between them as a small faster on-chip SRAM buffer.
- [model] Memory is modeled as an array of bytes, each 8 bits, addressed by index. A word is the unit a machine transfers at once.
- [definition] An array whose elements are arrays forms a matrix. Ten outer slots, each holding a four-slot REAL array, can be written ARRAY 10, 4 OF REAL, with M[i,j] selecting row i, column j.
- [definition] Sequential access reads by stepping from an element to its successor and writes by appending at the end; only the current element is directly reachable.
- [mechanism] Fetching data from RAM takes far longer than processing it, often hundreds of CPU cycles on current hardware, so processors rely on cache, which holds streamed copies of memory. When: Estimating the cost of a cache miss. Why: Main memory latency is far larger than register or cache access time. (x2)
- [mechanism] Persistent data structures return a new object on each change while sharing data with the old one, so keeping the old version is cheap and undo just switches back to it.
- [mechanism] Memory is fetched in blocks, so after one access nearby data is cheap to reach; this is locality of reference, and a miss costs a slow fetch of a new block. When: Successive accesses fall in nearby addresses. Why: Hardware loads neighboring data with each request, so sequential access reuses it.
- [mechanism] Knowing a variable's range of values lets the compiler allocate storage statically, avoiding dynamic allocation, which is often key to efficiency.
- [rule] In production code, store neural network weights in arrays indexed by neuron number rather than searching input lists for a weight. When: Implementing a neural network for production use. Why: Searching lists for weights is slow.
- [rule] For data processed in sequence, store the actual values contiguously one after another rather than as pointers to scattered objects. When: Single-threaded loops over many items. Why: Neighboring items are already in the loaded cache line when needed.
- [rule] When pooled types vary, check object size against the slot size, since an oversized object in a small slot corrupts adjacent memory.
- [heuristic] Split a pool into size-specific pools when object sizes vary widely, since large slots holding small objects waste memory. Speed-efficient memory managers keep several block sizes and allocate each request from the matching pool. When: object sizes vary widely. Why: Large slots holding small objects waste memory.
- [heuristic] Pool objects that are created and destroyed often, are similar in size, are slow or fragmentation-prone to allocate, or wrap expensive resources such as connections.
- [heuristic] Skip creating new effects like particles when the pool is full, but kill the quietest existing sound when a new important sound needs a slot. When: the pool is full. Why: A missing new particle goes unnoticed, while a silent important sound is more noticeable than a cut-off one.
- [heuristic] Pack array components only when several fit in a word, especially when the storage saved is a factor of two or more.

## service locator
- [model] Service locator implementations vary on three questions: how the service is located, what happens when it cannot be found, and whether its scope is global or class-restricted.
- [model] The pattern has three roles: a service interface defining operations, concrete providers implementing it, and a locator that finds and hands out an appropriate provider.
- [definition] Service Locator is a dedicated class giving global access to a service via an abstract interface; unlike Singleton, it decouples callers from the concrete class and from its source.
- [definition] Singleton restricts a class to one instance and provides a global access point to it.
- [mechanism] Global state makes code harder to reason about, because a function reading it depends on code far away from it.
- [mechanism] A compile-time locator holds one static service whose type is chosen by preprocessor conditionals, such as a debug or release flag, so the choice is fixed per build.
- [mechanism] Because the service is chosen at build time, a successful compile guarantees it exists, and the accessor is usually inlined, leaving minimal runtime cost.
- [mechanism] Because the registering code builds the provider, it can supply runtime data the locator cannot know, such as a remote address for a networked service.
- [mechanism] Registered providers can be replaced while the game runs, so a null service can temporarily disable a system such as sound during testing.
- [mechanism] Global scope encourages all code to share one service, so no code has a reason to create its own provider.
- [mechanism] A simple service locator stores a pointer to a service in a static member, exposes a static accessor to fetch it, and a static provide operation so outside code can register an implementation.
- [rule] In a game engine, use a single central world interface for stability and reuse.
- [rule] An abstract service interface should have a virtual destructor and pure virtual operations, with no implementation of its own. When: Defining a service that concrete providers implement. Why: Keeping the interface free of implementation lets providers be swapped freely.
- [rule] Let callers find a service by name through one central lookup, so the service owner controls how it is found and replaced. Why: Changes then touch one place instead of every caller.
- [rule] Any code can request a globally located service, so it must behave correctly in every calling context.
- [rule] Treat a failed service lookup as a fatal bug and assert when it should never happen. When: Failing to find the service is a fatal bug.
- [rule] Reserve a service locator for singular, ambient facilities such as audio devices or display systems, and for cross-cutting concerns such as logging. When: When passing the object as a parameter would clutter code or thread through many layers.
- [rule] Making the component manager a singleton is an easy fix, but it inherits Singleton's problems, so read about Singleton before adopting it.
- [heuristic] Use the Singleton pattern only when a class truly cannot work correctly with more than one instance, and use it sparingly. Why: Singleton is applied more often than it deserves, and reaching for it by default is a mistake; it is often misused as a convenience for global access.
- [heuristic] Bind services at compile time when the choice is fixed per build and speed and guaranteed availability matter more than runtime swapping. When: The service must not change while the game runs.
- [heuristic] Restrict a service to a class when it serves one game domain, such as a network service used only by online classes; make it global when widely used, such as logging.
- [heuristic] Use a service locator sparingly, since globally accessible objects invite the same problems as Singleton.
- [heuristic] Choose internal initialization when objects must stay hidden; choose external when objects have many init variants and a simple pool interface is preferred.

When: A base class has several operations for one outside system. Why: One getter replaces several base methods and limits base coupling to the helper.
- [procedure] 1) Make the constructor private. 2) Hold a static instance pointer. 3) Provide a public static accessor that creates the instance on first call and returns it.

- [tradeoff] Routing all requests through one method keyed by a request code lets new checks be added without changing the interface, and makes all activity loggable, at the cost of an extra lookup step.
- [tradeoff] A runtime flag check catches duplicate construction only when it runs, whereas Singleton's guarantee is enforced at compile time.
- [tradeoff] A single global Game object exposing systems through getters reduces the number of separate globals but couples all code to the Game object. When: Reducing the number of global objects is the priority.

When: Base operations need a shared service that callers should not have to pass in. Why: Callers are relieved of supplying state, but the base now depends on the locator to find it.

When: Deciding who creates an entity's components. Why: Self-building guarantees completeness; injection gives flexibility.
- [tradeoff] Compile-time binding gives speed and guaranteed availability, but changing the service requires recompiling and restarting the game.
- [tradeoff] Global scope makes one shared service easy to reach but gives up control over where and when it is used; class scope keeps coupling controlled at the cost of repeated lookup code.
- [tradeoff] A locator is a more flexible and configurable cousin of Singleton that adds flexibility with little runtime cost, but used poorly it carries all of Singleton's baggage and worse runtime performance.
- [pitfall] A singleton is global state in a class, carrying hidden dependencies and coupling; global access lets any code include a header and reach objects the architecture meant to keep separate.
- [pitfall] A singleton's restriction on instance count spreads to every call site, so splitting the class later, such as a Log split into per-domain loggers, is costly.

- [tradeoff] Moving types into data gains flexibility but loses compiler management of class data and makes type-specific behavior harder to express. When: choosing a data-driven type object design. Why: The compiler no longer tracks type lifetimes and behavior must be modeled manually.
- [tradeoff] With open-source engines a team can change the engine to fit a new idea; other engines permit only scripting within existing features.
- [tradeoff] Open source scripting languages are free and modifiable, but some licences require releasing your own product or modifications as open source, and without a vendor nobody takes responsibility for faults or patent and copyright claims. When: Considering a free scripting language for a commercial product.
- [pitfall] Bundling single instantiation into the class forces that limit on code that only wanted convenient access, and it becomes entrenched at every call site.
- [pitfall] In deterministic games that keep players in sync, reading state outside the synchronized set can cause hard-to-find non-determinism bugs. When: Game logic depends on lockstep or deterministic simulation for network sync. Why: Values outside the synchronized state can differ between machines, so simulations diverge.
- [pitfall] Exposing a type object makes it part of the typed object's public API, which widens what must be maintained. When: choosing to expose a type object. Why: Callers may come to depend on the type, so changing it becomes costly.

## dirty flags and caching
- [model] A concrete polling station keeps, for each cached boolean topic, a value and the frame when it was last refreshed, in slots keyed by group and topic.
- [definition] A dirty flag marks derived data as out of date after its primary data changes, and is also called a dirty bit. When: Caching derived values such as world transforms. Why: The flag tells later code whether a costly recomputation is needed.
- [mechanism] When an algorithm touches scattered data, each cache miss stalls the CPU for a few hundred cycles while main memory is fetched; a cache hit reads quickly. (x2)
- [mechanism] On a cache miss, the CPU loads a contiguous cache line, typically 64 to 128 bytes, so memory adjacent to recently accessed memory is reached faster than arbitrary memory. Why: Neighboring data arrives with the requested byte.
- [mechanism] Pointer-based traversal adds an indirection per access; contiguous arrays keep needed data adjacent in memory, improving cache use and speeding up loops.
- [mechanism] Dirty-flag batching computes each affected derived value once per batch of changes, and skips objects whose inputs never changed or were removed before use. When: Many primary changes occur between uses of the derived data, such as once per frame before rendering. Why: Chained changes collapse into one recalculation, and unused results are never computed.
- [mechanism] Caching world transforms with a dirty flag passed down the traversal lets a render pass recompute only changed world transforms, since a node is dirty if any ancestor was dirty. When: Scene graph rendering where the world transform is read only by the render pass. Why: Ancestor changes reach descendants through the traversal flag, so no per-child marking is needed during the update.
- [mechanism] Refreshing world transforms immediately on each local change repeats work when several ancestors change in the same frame, since a world transform can depend on several changed local transforms. When: Multiple ancestors of an object change within one frame. Why: Each immediate refresh is thrown away when the next ancestor changes.
- [rule] Use dirty flags only when primary data changes more often than derived data is read; skip them when derived data is read after nearly every change. When: Considering a dirty flag for derived data that is hard to update incrementally. Why: Frequent changes relative to reads clear flags only after data is stale again, and a flag set on every read skips no computation.
- [rule] Cache or pass back the evaluated score so identical parameters are not evaluated twice by the driver and the step function. When: score evaluation is expensive. Why: recomputing wastes time.
- [rule] Store the hash in the board object and update it inside the move-making routine, so the hash is not recalculated from scratch on each request. Why: full recalculation is costly.
- [rule] Every code path that modifies primary data must set the dirty flag, because a missed path leaves stale derived data that causes hard-to-track bugs. When: Caching derived data behind a dirty flag. Why: Derived data is a cache, and invalidation is the hardest part of caching.
- [heuristic] Cache a topic when it is requested repeatedly within a frame.
- [heuristic] Caching world transforms pays off when many objects are static; eager refresh is acceptable when few objects change and each change is independent. When: Choosing between caching and eager refresh of world transforms.
- [heuristic] Cache derived data behind a dirty flag for slow calculations when memory is cheap; compute on demand when time is plentiful and memory is scarce. When: Deciding between caching and on-demand computation.
- [procedure] 1) If the stored frame is older than the current frame, call the game query. 2) Save its result as the new value. 3) Store the current frame number. 4) Return the stored value.
- [procedure] 1) On changing primary data, set the dirty flag only, with no computation. 2) When the derived value is needed, check the flag. 3) If set, recompute and clear the flag; otherwise reuse the cached value. When: Derived data is costly to compute and read less often than primary data changes. Why: Deferring recomputation to the point of use collapses many changes into one calculation.
- [metric] Each supported polling topic costs constant time and memory to access, excluding the cost of the underlying polling query.
- [tradeoff] Skipping clean-node math saves computation, but the new conditional branch can cause mispredictions and pipeline stalls that offset the savings. When: Adding dirty-flag branching to a hot render loop on modern CPUs. Why: Branch mispredictions cost cycles, so the saving is not guaranteed.
- [tradeoff] Fine-grained dirty flags process only changed data but cost more memory and per-chunk overhead; coarse-grained flags save memory and overhead but may process unchanged data. When: Choosing the size of the unit tracked by a dirty flag. Why: Flag count drives memory and metadata cost, while unit size drives redundant processing.
- [tradeoff] Keeping derived data in memory speeds reuse but uses memory; computing it on demand and discarding it saves memory at the cost of repeated computation. When: Choosing whether to store derived data behind a dirty flag. Why: Memory and computation trade against each other.
- [pitfall] Cache setups differ across PCs, consoles and mobile devices, so performance measurements taken on one machine may not hold on others.
- [pitfall] The dirty-flag traversal is only safe when render is the sole reader of the cached world transform; other readers need a different approach. When: Caching world transforms alongside a dirty-flag render pass. Why: Other readers would not trigger the recomputation and could read stale values.
- [fact] A processor can work only on data in cache, and operating-system address translation can add constraints such as aliasing failures between addresses.
- [fact] On 32-bit PCs, data structures larger than about a megabyte are hard to manage for cache performance.
- [fact] A full implementation would need several cache classes, one for each data type.
- [fact] Cache levels L1, L2 and L3 grow larger and slower with each step outward from the CPU.
- [fact] Cache-hostile memory access can make identical computation about fifty times slower than cache-friendly access.
- [fact] A cache line-sized block, for example around fifty items, is fetched per miss, and only one block fits in the fast store at a time. When: Explaining why sequential access beats scattered access. Why: Neighbors arrive together, so reading them in order costs one fetch per block.
- [fact] Cachegrind is a free profiler that runs a program on a simulated CPU and cache hierarchy, reporting all cache interactions. When: Measuring cache misses without commercial tools. Why: Simulation reports misses per location without requiring specific hardware counters.
- [fact] The dirty flag pattern applies to calculation work, such as transform math, and to synchronization work, such as writing data to disk or sending it over the network.
- [fact] Web frameworks and physics engines use dirty flags to mark data needing processing, letting unchanged data be skipped.

## observer pattern
- [definition] The notification queue must stay sorted by time, so it is implemented as a priority queue.
- [definition] Observer lets you observe the object that did something interesting, while an event object lets you observe an object representing what happened.
- [definition] The observer pattern has two roles: an observer interface with one notification method, and a subject that keeps a list of observers, offers public add and remove methods, and notifies each in turn. When: when implementing observer-based communication.
- [mechanism] A registry records each listener's interests so the checker searches only relevant items and the dispatcher delivers only matching events.
- [mechanism] Nearly every gameplay change requires code changes, and modular design limits how far a single change spreads through the codebase.
- [mechanism] With observer, listeners can be changed or removed without editing the subject, which keeps sending notifications that nothing receives. Why: The subject does not depend on any particular listener.
- [mechanism] Deleting an observer that a subject still references leaves the subject notifying freed memory; deleting a subject leaves observers waiting for notifications that never arrive. When: when observers or subjects are destroyed while registered. Why: registration links are one-directional bookkeeping that the destroyed object cannot clean up on its own.
- [mechanism] In an intrusive linked list, observers themselves carry next pointers and the subject keeps a head pointer, so registration and notification need no dynamic allocation. When: when avoiding allocation for observer registration. Why: the list nodes are the observers, so no separate node objects are needed.
- [mechanism] When one observer watches several subjects, each subject's list uses separate node objects that point at observers, so one observer can sit in multiple lists at once. When: when an observer must watch several subjects. Why: each node carries its own next pointer, freeing the observer from a single link.
- [mechanism] In a GUI, the operating system queues user input and the app's loop pulls the oldest event and routes it to a handler, unlike interrupts that force a jump at any moment. Why: The app chooses when to pull events.
- [rule] Unregister observers when no longer needed; a subject keeps references to them, so garbage collection cannot reclaim them and they keep receiving notifications (lapsed listener problem). When: Observers are created and abandoned without unregistering. Why: Subjects retain their listeners; the subject's reference keeps the observer alive.
- [rule] Use observer to decouple mostly unrelated subsystems or a feature reacting to events from several unrelated domains; avoid it inside one cohesive feature. Why: Observer suits decoupling, not tightly coupled logic; the subject announces events without knowing its listeners.
- [rule] Register a listener for a specific trigger, such as a set time, rather than for repeated updates it would ignore each frame.
- [rule] Have each observer unregister itself from its subjects in its destructor. When: when the observer knows which subjects it watches. Why: the simplest way to prevent dangling observer pointers.
- [rule] Give the observer interface a virtual destructor and one pure virtual notification method that receives the sending entity and an event identifier. When: when defining an observer interface in C++. Why: the virtual destructor keeps polymorphic deletion safe.
- [rule] A concrete observer should switch on the event identifier and act only on the events it cares about. When: when one notification method serves many event kinds. Why: ignoring unrelated events keeps each observer focused.
- [rule] Keep observer handlers fast: return quickly and move slow work to another thread or a work queue. When: when an observer must do expensive work. Why: blocking the notifying thread stalls the subject and the game.
- [heuristic] Indirect call overhead matters little when the work is spread across frames, since the overhead is spread too. When: work is spread across frames.
- [heuristic] If understanding one side of a communication requires understanding the other, use an explicit call instead of an observer. Why: Observer hides the link between the two sides.
- [heuristic] Use observers for communication outside performance-critical loops, where the cost of dynamic dispatch is affordable. When: when deciding where observers belong. Why: hot code paths are sensitive to per-call overhead.
- [heuristic] Register functions or closures as observers instead of implementing a full observer interface, which feels heavyweight when only one notification is needed. When: when the language supports first-class functions. Why: a single class cannot easily use different notification methods for different subjects.
- [procedure] 1) Take notifications from the front of the time-sorted queue. 2) Deliver each one whose time has passed. 3) Stop at the first notification scheduled in the future.
- [procedure] 1) Place a reference to the sender inside the event object. 2) Listeners read that reference when they need to know who sent the event. When: A listener needs to know the sender. Why: Multi-writer queues do not otherwise reveal the origin of an event.
- [tradeoff] Making a class observable by inheriting from Subject exposes notify only to the class itself, but composing a separate event object keeps the class hierarchy free of the base class. When: Making an engine or system observable. Why: Production code usually prefers composition over inheritance.
- [tradeoff] Keeping observers in a collection, not one slot, keeps them independent, because one registration cannot silently unhook another. When: when a subject can have several observers. Why: one slot means a new registration can replace an existing one.
- [pitfall] Observers that add or remove observers during notification can corrupt the subject's list, so notification must prevent or handle concurrent modification. When: when notifying a list that observers may modify. Why: the notify loop walks the list while observers change it.
- [pitfall] Observers should not depend on notification order, since depending on it signals hidden coupling between them. When: when observers are notified in list order. Why: list order is an implementation detail that can change.
- [pitfall] An observer that tries to acquire a lock held by the notifying subject can deadlock the game. When: when observers and explicit locks are mixed. Why: the subject waits on the observer while the observer waits on the subject's lock.
- [pitfall] Observer is often confused with events and messaging, which are distinct patterns, and the confusion makes communication harder to reason about. When: when naming or choosing a communication pattern. Why: the patterns differ in coupling and timing.
- [fact] Indirect calls usually carry a far higher cost than direct ones, chiefly via pipeline stalls and cache effects rather than extra load.
- [fact] Plain function pointers hold no state, so a command that needs stored data requires a class or functor. When: in languages where function pointers lack closures.
- [fact] Observer notification walks a list and makes virtual calls, with no message objects or queues, so it is slower than a direct call but negligible outside hot code. When: when judging observer overhead. Why: virtual dispatch costs little unless it runs in tight loops.

## entity component systems
- [model] An entity is just a numeric ID binding components stored in separate collections; components know their entity's ID and find siblings by it, so adding components needs no entity change. When: Entities need open-ended component sets. Why: The entity has no fixed structure to modify.
- [model] An abstract entity declares a pure virtual update(), and a world holds pointers to entities and calls update() on each once per frame.
- [definition] Data Locality arranges data so that data processed together is contiguous in memory in processing order, keeping the CPU cache full as the loop runs over same-type objects.
- [definition] Component pattern lets one entity span several domains without coupling them: the entity owns components, each handling one domain (input, physics, graphics, sound, AI) and delegates its work to them. When: one entity must cover several game domains; structuring an entity with the Component pattern. Why: Isolated domain classes keep input, physics, graphics, sound, and AI from depending on one another; the entity delegates domain work instead of implementing it.
- [definition] Data-oriented design arranges data in memory for cache-friendly access, treating data layout as a key part of performance design. When: Performance-critical code touches large amounts of data. Why: Access patterns, not object abstractions, determine most of the cost.
- [mechanism] Entity variants such as decorations, zones, and props can be built from one GameObject class plus optional physics and graphics components, avoiding subclasses and duplicated code. When: Designing game entities that differ only by which capabilities they have. Why: Each entity plugs in only the parts it needs, so no class combinations must be hand-written.
- [mechanism] Larger component structs fit fewer per cache line, so unused cold fields dragged into every frame reduce the useful data a loop gets from each cache line.
- [behavior] Fetching components from a container adds indirection, which can slow performance-critical inner loops, although components can improve cache coherence. When: Tight inner loops access components through pointers. Why: Each access must first look up the component.
- [rule] Keep data that different threads modify on separate cache lines, since modifying nearby data across threads causes costly cache synchronization. When: Multithreaded code.
- [heuristic] Large class hierarchies are hard to manage, so engines often model entities with Component and Type Object patterns instead of one class per kind. When: when a game has many entity kinds. Why: composition avoids deep hierarchies.
- [heuristic] Entities that are off-screen or not yet unlocked, such as guards, can be moved out of the active list until they are needed.
- [heuristic] A plain array of entity pointers with a count suits a small sketch; production code should use a proper collection class.
- [heuristic] Data locality can speed up looping over many entities or components each frame, and is worth considering once profiling shows cache misses.
- [heuristic] Updating entities one domain at a time, such as all AI then all physics, makes it easy to slice components into cache-friendly groups. When: Entity components are processed in separate passes each frame. Why: Each pass touches one kind of data, so the working set stays small.
- [procedure] 1) Allocate one large contiguous array per component type, sized for the maximum entity count. 2) Store components by value in those arrays, not as pointers. 3) Loop by indexing each array directly. When: performance-critical update loops.
- [procedure] 1) Move the input-reading code into a component whose update takes the owning entity. 2) Expose position and velocity on the entity so components can read and write them. 3) Have the entity hold the component and call its update first. When: Splitting input handling out of an entity's update. Why: Components hold no position data, so they must receive the entity.
- [procedure] 1) Move motion and collision into a physics component that owns the collision volume. 2) Move sprite selection and drawing into a graphics component. 3) Keep shared position and velocity on the entity and call components in their original order. When: Completing the split of an entity's update into components. Why: Shared state stays with the entity, and order preserves correct results.
- [procedure] Apply the component pattern when a class touches domains that must stay decoupled, when a class has grown massive, or when inheritance cannot precisely select reusable parts. When: Deciding whether a class should be split into components. Why: Each signal indicates the monolithic design is costing more than it gains.
- [procedure] 1) Store an abstract ID per component in the entity. 2) Resolve the ID through a component manager using a linear search for a stored unique ID or a hash table mapping IDs to current indices. When: When components must move in memory.
- [procedure] 1) If component size s is not a whole number of words, round it up to S. 2) Leave S minus s words unused per component. This unused space is padding.
- [tradeoff] Flat component arrays speed hot loops but make entity handling less direct; a retained entity wrapper pointing into the arrays keeps non-performance code simple.
- [tradeoff] Putting update() on the entity class is simplest but scales poorly as entity kinds grow; putting it on components lets parts like rendering, physics and AI update independently.
- [tradeoff] Components holding direct references to a peer and calling its methods is simple and fast, but tightly couples that pair while keeping coupling limited to the pair. When: two closely related components must communicate. Why: Direct calls are cheap, but each component depends on the other's interface.
- [tradeoff] Components add complexity: each object becomes a cluster of instances that must be created, initialized, and wired together, and communication and memory layout become harder to manage. When: Deciding whether to adopt components. Why: The pattern trades simplicity for decoupling and reuse.
- [tradeoff] Entities holding raw component pointers give one-hop access and ignore component placement, but break when components move; entities holding component IDs resolved by a manager allow packing and moving at the cost of lookup speed and complexity.
- [fact] Components stored in flat arrays can keep their own data and methods, so encapsulation is largely preserved.
- [fact] The base state's update returns a result holding actions, a pending transition and a level, and by default returns the state's own action.
- [fact] Component is the common game-industry name for this pattern, and it is also the name of an unrelated business-software pattern. When: searching for or discussing the pattern. Why: The shared name can cause confusion when reading other sources.
- [fact] Unity's core GameObject is built around components, Delta3D's GameActor uses an ActorComponent base, and XNA's Game class owns GameComponent objects that apply the pattern to the whole game. When: Looking for production examples of the component pattern. Why: Several major engines adopt it.
- [fact] CPU speed has grown much faster than RAM access speed since 1980, so programs often wait on memory rather than computing. When: Judging whether data-heavy code is limited by compute or memory. Why: Processor gains outpace memory latency improvements.

## object pooling
- [definition] An object pool is a store that tracks a set of instantiated objects so they can be found and reused. When: Holding lazily created flyweights. Why: A pool gives a natural place to keep existing shared instances.
- [definition] Object Pool keeps a fixed collection of reusable objects allocated up front, handing them out and reclaiming them instead of allocating and freeing each one individually. Why: Trades flexibility for fewer allocations and less fragmentation.
- [mechanism] Infer in-use status from existing state, not a stored flag: a particle is in use while its lifetime counter exceeds zero; a coupled object may be unused when offscreen.
- [mechanism] Serving pathfinding requests from a shared pool of pathfinders fed by one queue, instead of one planner per character, reduces total memory use. When: Many characters request routes at once, such as in RTS or MMORPG servers. Why: Per-character planners hold large data that may exceed cache, while a fixed pool reuses stored data across requests.
- [mechanism] Particle systems store particles in one contiguous pool, but most slots are often inactive. Skipping inactive entries by testing a flag still pulls unused data into the cache. When: Pool is sized for a maximum count and many slots are unused at any moment. Why: Checking the flag loads the whole particle block, so inactive entries waste cache bandwidth.
- [mechanism] Pool allocates one block at startup and does not free it during play; each object tracks an in-use state, and reclaiming it just resets that state, so the memory manager stays out of the loop. Why: Avoids repeated allocation and freeing cost.
- [mechanism] Faster planning lets fewer pathfinders serve the same load, so total memory can fall even though each pathfinder stores more data. When: Pooled pathfinding with reusable stored results. Why: Fewer active pathfinders means less total stored data.
- [rule] Partition memory into separate pools per object type, since a fixed limit caps one type so a flood (explosions) cannot exhaust memory for others (new enemies). When: one object type could crowd out others.
- [rule] Set every field when reinitializing a reused object, and clear the slot in debug mode on reclaim, since reuse skips the memory manager's debug fill that catches uninitialized memory.
- [rule] Call the pool's update once per frame, looping over every slot and updating each object, with inactive objects doing nothing.
- [rule] A single pool with mixed object sizes must make each slot fit the largest object, and an undersized object write can overwrite its neighbor. When: objects of different types or subclasses share one pool.
- [heuristic] Tune pool size deliberately: keep it no larger than expected peak use, since extra slots waste memory; undersized pools usually surface as crashes.
- [heuristic] Object Pool management lets objects be added and removed in a contiguous array over time, which locality-focused designs usually rely on. When: Objects are created and destroyed often in performance-critical code. Why: Reusing slots keeps the array packed without repeated heap allocation.
- [heuristic] Spawned room contents such as enemies or items are good pooling candidates because they need reliable slots. When: generating or spawning dungeon room contents.
- [heuristic] Pooled pathfinding benefits most in persistent worlds where levels stay active for long periods, and less in RTS games, though it is worth trying when pathfinding is a bottleneck. When: Choosing whether to pool pathfinders. Why: Persistent levels keep reusable stored data valid for longer.
- [heuristic] When each path is short and computed in one go, use a small pool of planners with a request queue. When: Pathfinding with short paths.
- [procedure] 1) Preallocate a pool of identically sized nodes at startup. 2) Take nodes from the pool when observers register. 3) Return nodes to the pool on removal instead of calling the allocator. When: when observer registration must avoid dynamic allocation. Why: reusing fixed-size nodes avoids allocator calls during gameplay.
- [procedure] 1) Keep a static flag. 2) Set it in the constructor and clear it in the destructor. 3) Assert in the constructor that the flag is not already set. When: A class must stay limited to one instance without global access.
- [procedure] 1) Keep a head pointer to the first available object. 2) Have each unused object point to the next available one, with the last pointing to nothing. 3) Store the pointer in a union shared with live state. 4) Chain all objects together in the constructor. When: Implementing an object pool for particles or similar short-lived objects. Why: Chaining reuses dead objects' memory, so no extra array is needed.
- [procedure] 1) To create, take the head object off the list and initialize it, which takes constant time. 2) When an object dies, push it onto the front of the list. When: Using a free-list object pool.
- [procedure] 1) Scan slots from the start for the first unused object. 2) Initialize it with the new state. 3) Return it. 4) If no slot is free, drop the request.
- [procedure] Choose a full-pool strategy by comparing: 1) size the pool to never overflow, 2) skip creating the new object, 3) forcibly kill an existing object, 4) grow the pool at runtime or add an overflow pool. When: the pool has no free slot. Why: The right choice depends on how noticeable a missing new object is versus a disappearing existing one.
- [tradeoff] Pooling adds bookkeeping and fixed capacity, so it is wasteful when allocation is rare or cheap. When: allocation is rare or cheap.
- [tradeoff] Splitting pathfinding over frames to share a pool lengthens queue waiting time as the number of characters grows. When: Many characters requesting paths through a shared queue. Why: Requests wait longer while the fixed pool works through the queue.
- [pitfall] Type objects must be managed manually, and new typed objects without a valid type reference will break. When: using type objects without compiler support. Why: Nothing enforces that each typed object refers to a live, valid type.
- [pitfall] Free list pointers must be updated correctly on every create and destroy, and creating from an empty list must be guarded, or the list breaks. When: Implementing a free-list object pool.
- [pitfall] Because a pool's limit is hard, a burst of activity can exhaust it, so full-pool strategies must be decided in advance.
- [pitfall] Implicit allocation hides where storage sharing is intended, which causes problems when records are updated selectively.
- [fact] Object pools suit game entities, visual effects, and less visible structures such as the list of currently playing sounds.
- [fact] Pools are less common in garbage-collected systems but still help avoid allocation cost on slower mobile CPUs.

## performance optimization
- [model] Game performance work spans three layers: low-level hardware tuning, mid-level patterns, and algorithm research.
- [definition] SIMD applies one instruction to several data items at once, usually four at a time on current hardware.
- [mechanism] Keeping neuron states and weights in separate arrays lets SIMD instructions process four neurons at once and keeps relevant data in cache, giving large speed gains on big networks. When: Network is large and runs in production. Why: Contiguous data allows parallel arithmetic and better cache use.
- [rule] Do not route a hot loop through an entity object when it needs only component data; the entity adds an extra hop without useful state.
- [rule] Profile to reveal cache misses, then keep each algorithm's data together, since this often brings dramatic speed-ups.
- [rule] Clip velocity in the update step: if speed exceeds the maximum, normalize velocity and scale it to the maximum. Keep this out of the steering behavior itself. When: Acceleration-based movement with no other speed control. Why: Acceleration alone lets speed grow without limit.
- [rule] Keep slot costs well below the data type's maximum, since several costs are added together. Why: Summed costs can overflow.
- [rule] Cap the number of moves in any simulation or unbounded loop, for example at 500, and treat reaching the cap as the end, and keep the same safeguard in shipped code. When: running simulations or generators that could run indefinitely. Why: rare endless games or loops can hang the process, and small probability changes can make them common.
- [rule] Design a game that does not depend on special platform features from the start, especially if the team lacks time to learn that platform. When: when the team is unfamiliar with a target platform. Why: Unfamiliar platform features can consume scarce time.
- [heuristic] Unpredictable flag tests in hot loops cause branch mispredictions that flush the pipeline, so developers avoid per-item branches in performance-critical inner loops. When: Condition changes unpredictably between iterations of a loop running over many items every frame. Why: Branch predictors guess wrong on irregular patterns, each misprediction flushes the pipeline, and mispredictions and cache effects of branches add up across the loop.
- [heuristic] Check whether an optimized AI technique depends on C++-specific features before porting it, since such optimizations may not transfer to other languages. When: Porting optimized AI code to another language.
- [heuristic] SIMD and multi-core parallelism speed up AI only when the data and code are structured for them.
- [heuristic] Distance-to-nearest-enemy and flee-direction calculations suit SIMD well, and steering algorithms gain the most.
- [heuristic] Profile before abandoning flyweight for performance reasons, since its cost is often unclear without measurement. Why: Pointer indirection's cost depends on memory layout and may be negligible.
- [procedure] 1) Collect the behaviours due this frame using the frequency modulo test. 2) Count them. 3) Give each an equal share of remaining frame time and pass the share in. 4) After each run, subtract elapsed time from the remaining time before computing the next share. When: Frame has a fixed time allowance. Why: Overruns reduce later shares, keeping the total within the allowance.
- [metric] The load-balancing scheduler takes O(n) time and O(m) memory, where n is all behaviours and m the number due, and its two loops cannot be merged. Why: The share depends on the due count, so counting must precede running.
- [tradeoff] SIMD needs many characters performing the same operation with their data stored together, which restructures code and lowers readability. When: many characters run identical operations.
- [tradeoff] SIMD hardware can evaluate rules in parallel, but this drops the early-exit shortcut, since heavy branching parallelises poorly.
- [tradeoff] Bookkeeping structures use extra memory, so the pattern is a poor choice when memory is tighter than CPU time. When: memory is the scarcer resource.
- [tradeoff] Tally strokes make addition very simple but are poor for large numbers, while Arabic positional numerals make addition of large numbers, multiplication and division easier.
- [pitfall] Reference AI code omits platform-specific optimizations, which need machine-specific assembly and would obscure core algorithms, so profile it in your own game before shipping. When: Reusing sample or library code in a shipped game. Why: Code written for clarity carries little optimization.
- [pitfall] A single expensive behaviour, such as pathfinding, can cause a frame spike on its own, so long processes should be spread over several frames.
- [pitfall] Iterating a contiguous array and skipping inactive items does not restore locality when useful items are scattered among inactive ones. When: Active items are a small or interleaved fraction of the pool. Why: Skips jump across memory and the cache keeps reloading unused blocks.
- [pitfall] Conversion routines that ignore arithmetic overflow may produce wrong values for numbers too large for the integer type.
- [pitfall] Operation-count formulas ignore loop control and other overhead, and their coefficients depend on the system, so they cannot alone rank real run times.
- [fact] PC hardware varies widely; graphics APIs hide hardware differences but do not remove the need to detect features and adjust.
- [fact] Early power concerns were minor for mains-fed devices and handhelds, but phones and laptops made battery use central.
- [fact] Hardware pipelining imposes a floor of about three frames of input lag; input arriving mid-frame adds up to about four frame lengths. When: Standard multistage rendering pipeline.
- [fact] Running every expensive AI algorithm for every character each frame becomes impossible when a game has thousands of characters, as in real-time strategy.
- [fact] Online incremental algorithms give the largest speedups, and heuristics such as those in SITI can improve them further.

## coupling and modularity
- [definition] Coupled code means understanding one piece requires the other; decoupling lets each be reasoned about alone, and a change to one usually does not force a change to the other. Why: Decoupling is the main tool for making change easier, since the fewer places a change touches, the easier it is to make.
- [definition] The container acts as a Mediator, passing messages along without knowing what they mean. When: a container routes component messages. Why: Routing without interpreting messages keeps the container generic.
- [definition] Dependency injection means outside code passes a dependency into the object that needs it, rather than that object or a locator constructing the instance itself.
- [mechanism] The most common service locator design registers providers from outside code; the locator knows only the abstract interface while outside code constructs the concrete provider and registers it.
- [mechanism] A configuration file names the provider class, and reflection instantiates that class by name at runtime, so the service needs no compile-time reference.
- [mechanism] Disabling a service this way saves its memory and CPU and stops its side effects, such as sounds playing while a debugger is paused.
- [rule] Make callers, including entities, depend only on abstract interfaces rather than concrete classes, so providers can change without touching them. When: Components or services are supplied from outside. Why: Hides concrete types behind interfaces, supporting encapsulation.
- [rule] Skip registering a system's provider so a null service takes its place; wrapping that null service in a logger still logs the calls it would have handled. When: Disabling a system temporarily.
- [rule] Isolate and abstract modules from each other, giving each clear inputs and outputs, like objects with defined interfaces.
- [rule] Read pattern samples for the idea they express, not as models of production style, since sample code may avoid modern language idioms. When: studying pattern sample code. Why: Samples are written to teach ideas, not to demonstrate best practice in the language.
- [rule] Aim for decoupling where it lets one part of the code be understood or changed without the other, since less coupling means smaller ripple from each change. When: structuring game code modules. Why: Lower coupling reduces the knowledge needed before making progress.
- [rule] Share code between classes by having each own an instance of a shared class rather than inheriting from a parent. When: Two unrelated classes need the same behavior. Why: Composition avoids the hierarchy problems that inheritance creates.
- [rule] Do not expose a class that is valid only in one phase or context, such as simulation but not rendering, through a global locator. Why: Other code could call it at the wrong time.
- [heuristic] Before using a global, consider passing the object as a function parameter; this is simple, makes coupling obvious, and covers most needs. When: The object is core to the function's job, such as a rendering context. Why: Keeps dependencies visible in the signature.
- [heuristic] Avoid wrapping an outside call in an operation that only forwards to it, since the outside method can be called directly. When: An operation's only job is to pass the call to an outside system. Why: Pure forwarding adds little value; the exception is when it keeps a base class field, such as an engine reference, hidden from subclasses.
- [heuristic] Direct component references suit closely related domains such as animation and rendering, input and AI, or physics and collision. When: choosing a communication method between components. Why: Tightly related domains already depend on each other, so the coupling is acceptable.
- [heuristic] Use coupling when the pool serves one known object type and memory matters; use decoupling for a generic pool holding arbitrary types.
- [procedure] 1) Create the object with its parameterless constructor. 2) Call its init method with the remaining data. 3) Return the initialized object, so callers cannot skip initialization. When: Two-stage initialization is used and half-built objects must be prevented. Why: Wrapping creation in one function makes the init step unskippable.
- [procedure] 1) Give a component a pointer to its matching peer at construction. 2) Call the peer's methods directly when the state is needed. When: wiring components that belong to the same domain pair. Why: Construction-time wiring makes the dependency explicit and avoids lookups at runtime.
- [tradeoff] Config-driven locating lets designers swap services without source changes and lets one codebase run several configurations, but the infrastructure is heavy to build and maintain.
- [pitfall] Passing cross-cutting services such as logging or memory management as parameters clutters function signatures and a module's public API, where they do not belong. When: Shared services used by many functions. Why: Such concerns are unrelated to the module's core parameters, such as rendering parameters for rendering code.
- [pitfall] Direct calls from many gameplay areas scatter feature logic, such as achievements, through unrelated code like collision resolution. Why: Each trigger site must know about the feature.
- [pitfall] Conditions that mix several domains, such as collision, visibility, and sound, in one check make a change in one domain break others without warning. When: One class contains logic spanning physics, rendering, and audio. Why: Each domain depends on the others' internals.
- [pitfall] Deferring the connection between two code pieces to runtime adds flexibility but makes their dependencies harder to see by reading the code.
- [fact] Connection getCost and getToNode normally return stored values, so the connection class is rarely a bottleneck.
- [fact] Three patterns decouple code in different ways: Component separates domains within an entity, Event Queue decouples communicating objects in space and time, and Service Locator decouples code from the provider of a facility. When: choosing a decoupling pattern. Why: Each pattern decouples along a different axis.
- [fact] Shared facilities such as memory management, logging and random numbers are needed almost everywhere in a game.

## message queues
- [model] Narrowcast managers form a hierarchy: one per small group such as a team, a shared manager across groups such as a battalion, and one manager per side for global information. When: RTS-style games with many groups.
- [definition] A message is a request for a future action, such as playing a sound; it works like an asynchronous service API and usually has a single listener. Why: If other code could take messages, the queue would lose its value.
- [mechanism] Narrowcasting uses many specialized managers, with listeners explicitly registered to those likely to want most of their events, so nearly every delivered event is wanted.
- [mechanism] Narrowcasting wastes few events and keeps no per-listener interest records, so runtime is faster when listeners want nearly everything they receive.
- [mechanism] A queue decouples sender from receiver both statically, meaning who they are, and in time, meaning when work happens.
- [mechanism] With one writer the sender is implicit, since only one object can add to the queue, and one writer usually comes with multiple readers.
- [rule] Queued events must carry full details, since by handling time entities may be deallocated and nearby objects moved; the receiver cannot safely inspect the world. When: when designing events for a queue, or when events are processed later than they were raised. Why: The world may have changed since the event was raised.
- [rule] Use per-squad messaging to avoid ambiguity when the same script runs for multiple squads. When: Concurrent copies of a script for different squads. Why: Separate message channels keep each squad's signals distinct.
- [rule] Use a queue only when a push-style sender and a pull-style receiver must meet through a buffer; the queue supplies that buffer. When: Choosing between a queue and simpler decoupling patterns like Observer or Command. Why: Queues are complex and reshape architecture, so simpler patterns are preferred unless time decoupling is needed.
- [rule] Decide who owns a queued message, since it outlives the enqueuing call; options are passing ownership to the queue, sharing ownership, or letting the queue own pooled messages. When: Messages are queued rather than processed synchronously. Why: A queued message outlives its sender's call, unlike a synchronous notification on the stack.
- [heuristic] Keep the narrowcast hierarchy simple, since a tangled network of unrelated managers may cost more effort than it is worth.
- [heuristic] Use narrowcasting when in-game speed matters more than the effort of setting up registrations.
- [heuristic] Real designs mix communication methods: shared state for basic data such as position, direct references for closely related pairs, and messages for less important notifications; start simple and add paths as needed. When: designing communication between components. Why: Each method suits a different kind of data and coupling.
- [procedure] 1) Give every component a receive method that accepts a message. 2) Have the container send a message by looping over its components and calling receive on each. 3) Let components send messages to the container. When: components must notify each other without referencing one another. Why: A container routing messages keeps siblings decoupled from each other.
- [tradeoff] Narrowcasting setup needs substantial code to decide how listeners attach to the managers.
- [tradeoff] Single-cast keeps the queue an implementation detail, is more encapsulated, and avoids contention between listeners, but the sender only sees the methods the owner exposes. When: The queue is part of a class's API. Why: One owner pulls the queue, so no other listener competes for items.
- [pitfall] Characters changing groups during play require re-registration, which is hard when a group has been largely destroyed.
- [pitfall] A sender receives its own broadcast, so message feedback loops are possible. When: a container broadcasts messages to all components, including the sender. Why: Broadcast delivery includes the origin of the message.
- [pitfall] Queued work runs after the sending call has returned, so the sender cannot count on an immediate result.
- [fact] Event queues need not be global; they are useful inside a single class or domain as well.
- [fact] Event queues may pair one sender with one receiver, one with many, many with one, or many with many. Fan-in is the many-to-one case; fan-out is the one-to-many case.
- [fact] Garbage-collected languages keep a message in memory while it is needed, whereas in C or C++ the programmer must ensure the object lives long enough.
- [fact] Shared ownership keeps a message alive while any reference exists and frees it when forgotten; in C++ shared_ptr provides this.
- [fact] When the queue owns messages, the sender requests a fresh message from the queue, fills it in, and the receiver processes the same stored message; this backing store is an object pool.
- [fact] Message queue usually names a system that communicates between applications, event queues live inside one application, and publish/subscribe usually names large distributed systems.
- [fact] Queue readers come in three kinds: single-cast, where one owner pulls from the queue; broadcast, where every listener sees every event; and work queue, where each item goes to exactly one listener.

## vehicle and character motion
- [model] Character movement is built top-down: gravity pulls a capsule until it rests on the ground, each input-driven parameter has its own rule, and collision is the only broadly shared code.
- [model] A vehicle physics model tracks suspension compression, each tire's forward and sideways grip, motor speed, travel speed, mass, air drag and rotational damping.
- [model] Raycast suspension is tuned with global gravity, body mass, extra vehicle-only gravity, and per-wheel maximum distance, minimum distance, suspension force and dampening.
- [definition] A weapon CPPN takes four inputs, the particle's relative position px and py, and its distance dc from the firing point, and outputs velocity components and RGB colour. When: evolving particle weapons.
- [mechanism] Storing speed on the spline lets the game look up any car's exact position and speed at any time, so cars can be rendered directly.
- [mechanism] Thrust that adds force along the facing direction up to a maximum builds up over seconds and releases slowly, making the ship feel floaty. When: when tuning thrust acceleration and deceleration. Why: Slow ramp and slow release create inertia that the player must anticipate.
- [mechanism] In the slide state friction drops sharply, so the character slides along the slope at a rate set by its steepness, with slight steering at reduced force.
- [mechanism] Without dampening, a raycast suspension rocks with growing force and can launch the body. Dampening reduces each upward force as the suspension settles toward equilibrium.
- [mechanism] As a tire turns, its velocity direction changes, and the friction forces applied to it change with that direction.
- [mechanism] As a tow chain unfurls, it switches from a non-simulated object to a physically simulated one, and a simulated attached door swings outward at the same moment.
- [mechanism] A vehicle rig jiggles in response to changes in its mass and balance, so attaching or deploying parts produces visible physical reaction.
- [mechanism] Dynamic flora can move by linking plant motion physics to wind speed, so vegetation responds continuously to the environment's wind state.
- [mechanism] Read and Write each act at the rider's position and then advance the rider by one element.
- [rule] Make every internal reference in copied vehicle scripts match the new name, because mismatched references stop the copied vehicle from working.
- [rule] Change an internally simulated velocity with forces, rather than assigning position, to produce flowing, organic motion.
- [heuristic] Use the highest available muzzle speed to minimize flight time; with obstacle-heavy indoor layouts, fixed speeds may need trial and error. When: weapon muzzle speed can vary. Why: Higher speed shortens flight time, reducing the window for the target to move.
- [procedure] 1) Each frame, measure the difference between desired and actual velocity. 2) When the difference exceeds a threshold, adjust front and side tire friction along a response curve. 3) Apply the adjustment gradually over frames. Why: Gradual friction changes close the gap without abrupt snapping.
- [metric] Uphill slopes beyond about 45 degrees apply an opposing force that scales with incline, slowing the character, which can still climb up to about 60 degrees.
- [metric] Past about 75 degrees of incline, forward force cannot beat the slope force, so the character enters the slide state.
- [pitfall] Failing to zero vertical velocity on contact stores hidden energy: ledges send the character plummeting and ceilings make it stick.
- [pitfall] Rapid height changes such as curbs can make visible tires snap. Interpolation reduces this but cannot remove every odd case.
- [fact] A vehicle is built from three scripts: a behaviour script, a content script for effects and sound cues, and a factory script that spawns the vehicle actor in game.
- [fact] Weapon behaviour and sound references are defined in scripts, so changing a weapon's sound often begins as a code edit.

## state pattern
- [model] A state interface has four methods: getAction runs while active, getEntryAction on entry, getExitAction on exit, and getTransitions lists outgoing transitions. When: Designing a generic state machine. Why: Separating entry, active and exit actions lets each run at the correct moment.
- [model] The State pattern has a state interface with a virtual method for each state-dependent behavior, one class per state implementing it, and an owner holding a pointer to its current state.
- [model] Strategies are usually stateless and define how an object behaves, while components often hold state that defines what the object is; a stateless component can be shared and then behaves like a strategy. When: Distinguishing the Strategy pattern from the Component pattern. Why: State is the main difference between the two delegation forms.
- [mechanism] Assigning the owner's state pointer to a different state object changes how the owner responds to every delegated call.
- [rule] Add an undo method next to execute in the command interface, and have undo reverse the state that execute changed.
- [rule] Have a state's transition method return the next state so the owner swaps it in after the method returns. Never delete the current state from inside its own method. Why: Deleting an object while its own method is still running is unsafe.
- [rule] A state that holds data specific to one object must be newly created on each transition, and the owner deletes the old state after swapping.
- [heuristic] Use the State pattern when a conditional on state is complex enough to justify dynamic dispatch. A simple if is often all a small branch needs.
- [heuristic] A stateless state with only one method can be replaced by a plain function, with the state field holding a function pointer instead.
- [heuristic] Visiting every object to swap distributed state is acceptable when each object's state must be touched every frame anyway. When: Every piece of distributed state is cleared or rewritten each frame. Why: The visit cost is already paid by the per-frame work.
- [heuristic] Add jumps and procedures only once scripts need conditionals, repeated code, or reusable fragments. When: Growing a bytecode instruction set incrementally. Why: Simple scripts run fine without control flow, so adding it early adds complexity without benefit.
- [heuristic] The component pattern fits large codebases; in small projects it risks over-engineering a problem that does not yet exist. When: Choosing an architecture for a project of a given size. Why: Decoupling and reuse only repay their overhead at scale.
- [procedure] 1) Define a state interface with a virtual method for each state-dependent behavior. 2) Create one class per state, moving that state's switch cases into it. 3) Move state-specific data into the state class that uses it. 4) Have the owner hold a pointer to its current state and delegate calls to it. When: A switch on state keeps growing or state data is only meaningful in one state.
- [procedure] 1) Define a fixed set of predefined behaviors. 2) Store in each type which behavior it uses, such as a function pointer for AI. 3) Select the behavior from type data at runtime. When: type-specific behavior must vary without full scripting. Why: A fixed set keeps behavior manageable while type data picks among options.
- [procedure] 1) Make the input component an abstract base with a pure virtual update. 2) Implement a player input class and a demo input class against it. 3) Pass the chosen implementation to the entity through its constructor. When: An entity's control source must change, such as to an AI-driven demo. Why: Physics and graphics stay unchanged because they never see which input is used.
- [tradeoff] Recording full game state each frame makes replay simple but uses too much memory; recording per-frame commands is compact but needs re-simulation.
- [pitfall] Undo only works if every data change goes through a command, which requires discipline across the codebase.
- [pitfall] Allocating a new state object on every transition can fragment memory. An object pool can reduce the problem.
- [pitfall] Subclassing for every new behavior eventually produces hierarchies in which code cannot be reused cleanly.
- [fact] Stateless commands behave identically in every instance, so keeping many copies of one wastes memory.
- [fact] The State, Strategy, and Type Object patterns have similar structure. They differ mainly in intent.

## software design principles
- [definition] Reifying a concept means making it first-class: turning it into a piece of data you can store in a variable or pass to a function.
- [mechanism] Overzealous interfaces, base classes, and virtual layers slow tracing of real behavior and fill the developer's working memory with scaffolding. When: code has many layers of indirection. Why: Each layer must be traversed and held in mind to find actual behavior.
- [rule] Use numeric constants rather than strings for semantic identifiers in games, because string comparisons are slow. When: game blackboards. Why: string comparison costs runtime.
- [rule] Before building complex routing and filtering for queued communication, check whether a simpler design is enough. Why: Elaborate routing adds cost that simple designs avoid.
- [heuristic] Production code can drop polymorphic flexibility where it is not needed, which can speed up hot code such as pathfinding.
- [heuristic] Centralize a dependency in the base class when many derived classes share it, accepting a larger base class that becomes harder to maintain as it grows. When: Several subclasses need the same outside system. Why: One shared access point avoids repeating the dependency in every subclass.
- [heuristic] Calling a method that does not modify state is a safer form of coupling than calling one that changes state, so read-only calls are better candidates for shared access. When: Choosing which outside calls a base class should expose to subclasses. Why: A read-only call cannot break the game, while state-changing calls tie subclasses more deeply to the underlying code.
- [heuristic] Private constructors and friend classes can restrict object creation to a factory function. When: Two-stage initialization needs to force creation through one path. Why: Callers outside the factory are unable to construct the object directly.
- [heuristic] Keep heavy abstractions where performance matters little, and apply locality-focused layout only to bulk data processing paths. When: Choosing how widely to apply data-oriented layout in a codebase. Why: Locality has costs in flexibility, so it pays off only where data is processed in bulk.
- [heuristic] Hide a data structure's representation behind an interface so clients cannot break its invariants directly. When: designing a module that exposes a structure with an invariant. Why: Clients can then change the structure only through operations that keep the invariant.
- [heuristic] Design programs by reasoning with numbers, sets, sequences and repetitions rather than bits, storage units and jumps, which makes the design more reliable.
- [procedure] 1) Identify each domain's code in the monolithic class. 2) Move each domain into its own component class. 3) Have the main entity hold an instance of each component. 4) Reduce the entity to a minimal wrapper that links the components together. When: A class mixes several domains such as input, physics, and graphics. Why: Separated components can change independently.
- [pitfall] In a shared library used by several games, changing a global design means coordinating changes across several teams.
- [pitfall] Relying on the right operand of & or OR being evaluated is wrong, because it is skipped when the left operand decides the result.
- [fact] Listeners of a specialized manager, such as a collision manager, may want anything it can generate.
- [fact] Simple code often runs faster due to less overhead, but this is not guaranteed, since dense loops or recursion can still be slow.
- [fact] Simple code is not necessarily quicker to write than messy code.
- [fact] Six classic object-oriented patterns are Command, Flyweight, Observer, Prototype, Singleton and State.
- [fact] Certain limits arise from design consequences; others exist to keep frame rate acceptable.
- [fact] Representation decisions form a chain: early choices such as coordinate system depend on the problem, while later choices such as number format depend more on the tool and its technology.

## buffer management
- [definition] Double buffering makes a series of sequential updates appear simultaneous to observers, so update order is irrelevant because every object reads the previous frame's state.
- [definition] Buffering collects a stream of data in memory and transfers it in blocks, letting producer and block-oriented device run concurrently; sequential access allows this, using secondary storage far more effectively. Why: Devices such as tapes need fixed-rate data in large blocks.
- [definition] A buffered class keeps a current buffer and a next buffer of its state. Reads come from current, writes go to next, and a swap publishes finished changes at once.
- [definition] A circular buffer is a finite array used as a first-in-first-out queue with write and read indices that wrap around, plus a count n with 0 ≤ n ≤ N. Why: Fetched slots are no longer needed, so the array can be reused.
- [mechanism] A buffer decouples producer and consumer, so a slow consumer can catch up later; decoupling grows with buffer size and helps only when average rates match but fluctuate. When: Producer and consumer rates are about equal on average but fluctuate.
- [rule] The buffer swap must be atomic: no code may access either buffer while the swap happens.
- [rule] Fetch requires n > 0 and deposit requires n < N; in single-agent use, violating fetch's condition is a programming error and violating deposit's means the buffer is too small.
- [heuristic] Let the nature of the data decide buffer granularity: use one monolithic buffer for a single block of state and distributed buffers when each object owns its data.
- [procedure] 1) Apply each incremental edit to the next buffer. 2) When edits are complete, swap the buffers so the old current buffer becomes the next buffer and is reused.
- [procedure] 1) Choose buffer size N as a common multiple of producer block size Np and consumer block size Nc. 2) Track empty slots ne and filled slots nf separately. 3) Producer waits when ne becomes negative; consumer waits when nf becomes negative. When: Producer deposits blocks of Np elements and consumer fetches blocks of Nc elements.
- [procedure] 1) Copy the cells. 2) Right-click the target cell and choose Paste Special. 3) Choose Paste Values Only. When: A random or formula result must stop recalculating.
- [procedure] 1) Start with an array. 2) When it is full, double its size and copy the items over. 3) Enqueue then has constant amortized cost. When: Capacity may exceed a fixed bound. Why: Doubling spreads the copy cost across many enqueues.
- [tradeoff] A monolithic buffer swaps with a couple of pointer assignments. Distributed buffers require visiting every object to swap, so the cost grows with the object count.
- [tradeoff] Double buffering always needs twice the memory because two copies of the state exist. On memory-constrained devices, look for other ways to keep state from being accessed during modification.
- [fact] Double buffering works at the implementation level, so most of the rest of the codebase is unaware that it is used.
- [fact] The swap is often as cheap as assigning a pointer.
- [fact] Graphics APIs provide buffer swapping to avoid tearing: OpenGL uses swapBuffers(), Direct3D uses swap chains, and XNA swaps framebuffers inside endDraw().
- [fact] The full output sequence of a 64-bit generator cannot fit in typical memory, so seed candidates must be narrowed first.

## static and type object patterns
- [definition] The cardinality of a type is its number of distinct values, which measures the storage needed to hold it.
- [heuristic] Prefer a static class for single-instance behavior when only one instance is needed and neither lazy initialization nor polymorphism is needed.
- [heuristic] A state with no per-object data needs only one instance, which can be shared by many state machines and avoids allocation on each transition.
- [heuristic] Single inheritance is usually the best balance of power and simplicity for type data; multiple inheritance gives little duplication savings but is hard to reason about. When: choosing inheritance for type objects in games. Why: Single inheritance is simple to understand, which matters because non-programmers must work with the system.
- [heuristic] The owner of a service can publish a stand-in object instead of the real one, keeping the actual implementation hidden from callers.
- [procedure] 1) Keep a static flag. 2) Have the constructor check that the flag is clear and set it. 3) Clear the flag in the destructor. When: A class must be non-static but limited to one instance.
- [procedure] 1) Store shared attributes such as starting health and attack text in the type object. 2) Give the type a factory method that creates typed objects. 3) Copy starting values from the type into each new object. 4) Keep a reference to the type for lookups it forwards. When: implementing a type object with a factory. Why: The factory centralizes creation, and forwarding keeps shared data in one place.
- [procedure] 1) Take the cardinalities of the base types. 2) A record's cardinality is the product of its field cardinalities. 3) Repeat this combination upward through nested types.
- [tradeoff] Type Object delegates invariant identity data, while State delegates current configuration; a type object doubles as State only when its type may change at runtime. When: deciding whether delegated data is a type or a state. Why: Invariant identity and current configuration are different kinds of data; changing type over time makes delegated data behave like current configuration.
- [tradeoff] A static-instance singleton avoids lazy setup but loses polymorphism, requires static-time construction, and cannot free its memory.
- [tradeoff] Shared static states avoid allocation but cannot hold per-object data. Instantiated states hold separate data per object but cost an allocation on each transition.
- [tradeoff] A base class can hold shared state such as a particle system as a private static member set once by a static init, which saves per-instance memory and initializes once. When: All instances of the base class share one resource. Why: Static state avoids storing a copy per object, but it carries many singleton problems, since all instances share one object that makes reasoning harder.
- [pitfall] Old class names left inside any script break the link between renamed weapon files.
- [pitfall] A log stored as a static member of a base class is held by nothing outside that base class, but every derived class can reach it.
- [pitfall] Storing per-object data in a static state breaks as soon as two objects are in that state at once.
- [pitfall] Calling a service through a static class or singleton ties every call site to the concrete class and its access method, so later changes force edits everywhere.
- [fact] Type Object, Prototype, and Flyweight all share data among objects, but differ in purpose; Type Object focuses on organization and flexibility rather than memory savings. When: comparing type object to related sharing patterns. Why: Each pattern shares data for a different primary reason.
- [fact] A C++ vtable is essentially a type object, and an object's vtable pointer is its reference to that type. When: understanding type objects through language features. Why: The type object pattern mirrors the mechanism language compilers already use.

## script parsing and syntax
- [definition] Lex generates tokenizers and Yacc generates parsers from descriptions of a language's tokens and grammar; both output C code.
- [definition] A tokenizer splits the character stream into tokens such as names, operators, numbers, whitespace and end-of-statement markers, without working out how they fit together.
- [definition] A scanner reads the next item of text, reports its class (integer, real, name, string or special character), and gives its value.
- [heuristic] Yacc-generated parsers are as good as or better than hand-written ones unless the writer is an experienced parser author, and can be tuned further where speed matters. When: choosing between generated and manual parsers.
- [procedure] 1) Describe each token's pattern in Lex, such as what forms a number. 2) Generate C code that converts a text stream into token codes and token data. When: building a tokenizer for a scripting language. Why: Lex turns token patterns into a C scanner.
- [procedure] 1) Write the grammar in Yacc, stating which tokens combine and which larger structures are built from smaller ones. 2) Generate C code that parses the token stream. When: building a parser for a scripting language. Why: Yacc turns grammar rules into a C parser.
- [metric] Independent unification clauses are searched separately, each at most linear in database size, so m clauses cost at worst about n times m for n items.
- [tradeoff] Language notation trades familiar mathematical abstractions against efficient compilation; overly machine-oriented notations and fully representation-open notations both fall short.
- [pitfall] Lisp-style bracketed syntax is hard for programmers used to C-style languages, so an editor that checks bracket matching becomes essential.
- [pitfall] Hand-translating nested expressions into bytecode is error-prone, so real content needs a compiler-like tool to emit the bytecode. When: Writing bytecode for non-trivial expressions by hand. Why: Each step must be sequenced and tracked on the stack, and manual errors accumulate quickly.
- [pitfall] A recursive definition without a terminating alternative has infinitely many instances, which makes its values unbounded.
- [fact] Lex and Yacc are usually included with UNIX distributions and are available on other platforms; Flex and Bison are common Linux variants.
- [fact] Both Lex and Yacc allow custom C code to be attached to tokenizing or parsing actions.
- [fact] Lisp-style syntax is easy to parse, so compilation can be efficient, and the fastest Scheme versions can match other scripting languages.
- [fact] A parser may build a symbol table of variable and function names; this is optional, since some languages look names up at run time.
- [fact] Syntax errors are detected during parsing, because no tree can be built from invalid input.
- [fact] Apps where several matching rules can stack need fewer rules for overlapping conditions than apps that apply only the first match.

## flyweight pattern

- [rule] Keep shared flyweight objects immutable, for example with const methods, because a change would appear in every place that uses the object. Why: A single shared object affects all of its users at once.
- [rule] Use flyweight when there are too many objects, either from memory use or from the processing cost of each one. Why: Sharing reduces the number of distinct objects that must be stored or handled.
- [rule] Flyweight can replace an enum with many switch statements while keeping an object-oriented style without creating a huge number of objects. Why: Shared objects give behavior and data in one place.
- [rule] Store shared flyweight instances directly in their owning object rather than dynamically allocating them, which keeps lifetimes simple. Why: Owned members have predictable lifetimes.
- [heuristic] Keep position and velocity on the entity when almost every component uses them, which gives components a simple communication channel without coupling. When: Several components read the same state. Why: Shared data on the entity avoids direct component-to-component links.

## record types
- [definition] A record joins components of possibly different types into one compound value, forming the Cartesian product of its field types.
- [definition] A recursive record type refers to itself through pointer fields, and an extra NONE value can mark where such a structure ends.
- [definition] A recursive data type has components of its own type, just as a recursive procedure calls itself, and suits nested structures such as arithmetic expressions and family pedigrees.
- [mechanism] Because record field names are fixed, the compiler knows every field offset in advance, which makes record field access efficient.
- [rule] Select record fields by fixed field name using a dot, and chain selectors for nested fields. Array components are selected by computed index instead.
- [rule] Every recursive data type needs a variant (conditional) component so that its values are finite, just as a recursive procedure needs a conditional to terminate.
- [metric] A record field's offset is the sum of the sizes in words of all preceding fields, so the first field has offset zero.
- [metric] The number of possible values of a record equals the product of the number of possible values of each field.
- [tradeoff] Records allow fields of differing types but select each by its fixed identifier, with no computed selection; arrays hold uniform components selected by computed indices.
- [pitfall] Duplicating a shared record instead of pointing to it means an update through one path is not seen through the other.
- [fact] After a scan, the item's value is available in the field matching its class, together with the character that immediately follows the item.

## polymorphism and pointers
- [definition] A pointer type is declared as pointing to a given element type, and this binding fixes what the pointer may refer to.
- [mechanism] Reading a property through a pointer follows the pointer to the shared object, and this indirection can cause cache misses and slow access. When: Replacing a value with a pointer to a shared object. Why: The extra memory hop may not be in the cache.
- [heuristic] Consider a polymorphic value interface only for an open-ended set of value types that lies outside performance-critical VM code. When: Value types must be extensible by code outside the core VM. Why: Implementing a base interface lets new types be added without changing the core.
- [tradeoff] Base-class pointer arrays keep polymorphism and variable object sizes, but each element's pointer hop hurts cache locality; avoid them in tight per-frame loops over many objects. When: Acceptable when code is not performance-critical and flexibility matters more than speed; avoid when a tight loop processes many objects per frame. Why: Each element is reached through an indirection, so the extra pointer hop per element causes repeated cache misses.
- [tradeoff] Polymorphic match classes are clear but may run slower, while merging their data fields into one structure can be more efficient.
- [tradeoff] Representing VM values as a class hierarchy with virtual type tests and conversions is open-ended and clean, but verbose, heap-heavy, and slow for a VM core. When: Choosing how to represent VM values in an object-oriented language. Why: Each value is a heap object reached through pointers, and every access is a virtual call.
- [tradeoff] Packed arrays need uniform element size, so polymorphic subclassing conflicts with them. Avoid virtual dispatch in cache-critical code, or keep one homogeneous array per concrete type. When: Optimizing data-heavy code where object types vary. Why: Virtual calls and variable object sizes break contiguous, uniform storage.
- [pitfall] Storing entities and their components behind pointers, then updating them in passes, makes each step a likely cache miss, and the cost repeats every frame. When: Entities and components are allocated individually on the heap and updated in several passes. Why: Each pointer hop lands on a scattered heap address, so the CPU waits on memory for every component.
- [fact] A pointer is typically no larger than an enum, so the memory overhead of pointing to a shared object is almost nothing.
- [fact] Passing ownership means the queue claims the message on enqueue and the receiver deallocates it after processing; in C++ unique_ptr provides these semantics.

## set types and operators
- [model] A set of small integers is stored as a characteristic bit string with one bit per possible element, set to 1 when that element is present.
- [definition] SET denotes sets of small integers, typically from 0 to 31 or 0 to 63, with operators for union, intersection, difference, symmetric difference and membership.
- [mechanism] Union, intersection and difference of bit-string sets become OR, AND, and AND combined with the negated second set, applied to all bits together.
- [rule] Represent sets as bit strings only when elements are small integers. The largest usable element is the machine word length minus one.
- [rule] Store a bit-string set in a small, fixed number of words that support logical operations and shifts. Why: efficient set operations need these primitives.
- [rule] In SET expressions, * and / bind tighter than + and -, which bind tighter than IN, so x IN s + t reads as x IN (s + t).

- [procedure] 1) Shift the set's word so the tested element's bit lands in the sign position. 2) Test the sign bit, which is set when the element is present.
- [fact] Set literals are a singleton such as {5}, a range {x, y..z} holding x up to z, and the empty set {}.
- [fact] Set operators are * for intersection, + for union, - for difference, / for symmetric difference, and IN for membership.
