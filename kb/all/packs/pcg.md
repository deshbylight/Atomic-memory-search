## generated content evaluation
- [model] Direct evaluation comes in two varieties: theory-driven, built from qualitative theories of player experience and intuition; and data-driven, approximating content-to-affect mappings from questionnaires or physiological measurements.
- [model] Evaluation functions fall into three classes: direct, computed from content features; simulation-based, scored by AI agents playing the content; and interactive, with a human in the loop.
- [model] Aesthetic measures for generated games fall into three groups: intrinsic (from rules alone), playability (from self-play outcomes), and quality (from trends in play). The system used 57 measures.
- [definition] A direct evaluation function computes a quality value straight from features extracted from the generated content.
- [definition] An evaluation function maps a generated artefact to a number indicating its quality, such as playability, intricacy or aesthetic appeal.
- [definition] Simulation-based evaluation runs AI agents through generated content and scores it using statistics of their behaviour.
- [definition] Static evaluation keeps agent behaviour fixed during play, while dynamic evaluation uses an agent that adapts as it plays.
- [definition] An intensity map is a two-dimensional matrix of real numbers where each cell's value sets the brightness of the matching pixel.
- [definition] A rule set is fit if playing it against itself over many trials produces a non-trivial and interesting contest.
- [mechanism] When several players rate the same population, each candidate's fitness is the average of all players' scores, which smooths individual taste. When: when multiple raters share one population.
- [mechanism] Simulation-based generation starts from a base environment, such as a landmass, and runs processes like erosion and climate to shape its geometry.
- [behavior] A level judged well in isolation can still fail in a full game, such as walls placed over the player's start point, so combined games need evaluation through automated playouts. When: when assembling separately generated level components into a game. Why: Component quality does not guarantee the components cooperate.
- [rule] Choose qualities to optimise and how to formulate them; building an evaluation function is hardest, since a poor one makes search optimise the wrong thing or find no good content.
- [rule] Give generated levels and content a written description that other team members can check against, since level designers use the document to see how each level fits the overall structure. When: Content is produced by a generator. Why: A written design document keeps the overall vision communicated across a large, complex team.
- [rule] Generated content should not look machine-made; aim for believable output.
- [rule] Measure expressive range by a quality relevant to player experience, not by raw counts of possible configurations. Why: Raw configuration counts ignore how output plays, while player-relevant qualities reflect the experience itself.
- [rule] Evaluate generated rule sets as whole games, using evaluation functions or constraints, rather than judging isolated artefacts. When: When generating an entire game rather than content for an already existing game.
- [rule] Evaluate an evolved content generator using many samples of its output, not a single artefact. When: evolving generators with highly variable output. Why: One sample can miss the generator's real range.
- [rule] Everything a human can produce must also be something the computer can generate alone, so the set of available choices must be meaningful. When: In mixed-initiative PCG systems where a human co-creates content with the computer. Why: Expressiveness is what lets the system offer a meaningful range of choices to the human collaborator.
- [rule] Include designer constraints, hard or soft, in quality evaluation of generated content.

When: When players play through a large part or the entirety of the game. Why: Such runs expose engageability problems, such as stretches that are too easy or too difficult or goals that stop exciting players.
- [heuristic] A section of a generated dungeon can be tested with about six players at once to check its usability and pacing. When: When participants play only parts of a game rather than its entirety. Why: Usability tests focus on usability, with engageability issues also examined.
- [heuristic] Denial-and-reveal tests can be run on generated layouts to check whether players actually find and follow hidden rewards. When: validating a generated layout. Why: generated layouts need the same behavioral checks as hand-built ones.
- [heuristic] A generator that produces challenges the player cannot judge, or responses that arrive late, works against the conditions for flow. When: generating content for real-time play. Why: Enjoyment in flow depends on the difficulty being just right for the player's current skill.
- [heuristic] Test generated room layouts in gym-style rooms to see how quickly players reach or aim at exits. When: When checking whether players can complete a specific task in the game. Why: Short task tests measure specific metrics such as completion time and number of errors.
- [heuristic] Card sorting can show how players group generated items or rooms, helping define those categories. When: When a feature is still a prototype and nothing is implemented yet. Why: The categories players naturally use to group cards reveal how to organise the system.
- [heuristic] A required pass proportion of zero is common, so one passing check suffices and the search can stop early; if one check passes, most others usually pass too. When: When the required pass proportion for connecting two regions is zero.
- [heuristic] Judge a procedurally generated game by how many interesting stories it produces, and improve it as a story generator. When: Evaluating procedural generation. Why: Good games keep producing event sequences so striking that players want to retell them.
- [heuristic] Randomly generated layouts and placements can coexist with skill-based play when players can see the odds and have ways to respond. When: designing procedurally generated dungeons. Why: Exposed probabilities let players compute their odds, and several escape options mean no situation is unavoidable.
- [heuristic] Prefer direct evaluation when relevant features can be extracted cheaply from the content; data-driven variants first require player data to build the mapping. Why: Direct functions are fast and simpler to build, while mappings to fitness may depend on models of player style or affect.
- [heuristic] Measure dungeon quality directly by counting unreachable rooms.
- [heuristic] Judge personalised content with several evaluation functions based on the imitation agent's performance statistics, checking challenge and diversity for that player. When: When content is personalised to one individual player's play style. Why: A network trained to imitate the player drives candidate tracks in their place, so performance can be measured.
- [heuristic] Useful map checks include base fairness between players, room to grow each base, and equal access to nearby resources.
- [heuristic] Genre knowledge tells the evaluator what to measure: board games are judged on balance and multiple nontrivial strategies, shooters on pace, wave patterns and difficulty progression. When: When evaluating generated rules for one specific genre rather than games in general. Why: Genre-specific design knowledge is more mature and easier to formalise than criteria for games in general.
- [heuristic] Keep a human as judge when quality is subjective, unknown in advance, or too hard to formalise, and let the computer produce variants quickly. Why: Algorithms produce some content very well and very fast, but some aspects are still better made by people.
- [heuristic] Combining top-down statistics with bottom-up player evaluation gives a fuller picture of what a generator does and whether it suits the designer's purpose.

- [heuristic] Evaluate generated spaces by what the player actually sees, treating a visible view as the unit of analysis.
- [procedure] Use steering behaviors, a wander behavior plus obstacle and wall avoidance, to cover the level automatically, restarting from random locations and running only briefly. When: Generating log data automatically. Why: Explorers often get stuck and repeatedly cover a small region; restarts reduce stuck errors.
- [procedure] 1) Pick a random sequence from a precomputed table. 2) Compute the maximum streak of it and of a human-entered sequence. 3) Guess that the longer-streak sequence is the random one. 4) Break ties arbitrarily. When: judging whether a human-invented sequence looks random.
- [procedure] 1) Generate a level that fits a design theory. 2) Let the designer edit it. 3) Let the designer add constraints. 4) Regenerate only the affected portions of the level. Why: Alternating generation and human editing lets the designer modify output and add constraints for regeneration.
- [procedure] 1) Generate a candidate. 2) Test it against the criteria. 3) Repeat until a satisfactory solution appears.
- [procedure] 1) Run generated code and catch runtime exceptions. 2) Give mechanics that throw errors a zero or low fitness. 3) Test the remaining mechanics on a level that is unsolvable without them. When: when evaluating automatically generated game code. Why: Catching errors lets the search continue past broken mechanics.
- [procedure] 1) Pick metrics as axes. 2) Generate many pieces. 3) Score each piece on the chosen metrics. 4) Plot the results as a histogram or heatmap. When: When a generator can output far more content than a person could review by eye. Why: Heatmaps of scored samples expose biases that viewing a handful of outputs would miss.

- [tradeoff] Expressivity and diversity compete with reliability, since broader output makes consistent quality harder to guarantee, and measuring expressivity is non-trivial. When: When content must vary without looking like minor variations on one theme. Why: Fully random piece assembly produces nonsensical, unplayable levels, while a fixed output lacks variety.
- [tradeoff] Input-linked metrics only confirm a generator honours its parameters; independent metrics can reveal emergent behaviour but are harder to choose, so pick them as far from inputs as possible. When: When running an expressive range evaluation to reveal a generator's emergent properties. Why: Metrics that mirror inputs only confirm what was built in, while independent metrics can reveal emergent behaviour.
- [tradeoff] Direct evaluation is fast and often easy to implement, but some aspects of content are hard to express as direct features. When: When some element of game content resists being captured by a straightforward scoring formula. Why: Direct functions score features extracted from the content itself, so no simulation is needed, but some aspects have no easy direct feature.
- [tradeoff] Some map objectives conflict, so no single map maximises them all, yet certain objective combinations still give interesting, reasonably fair maps. When: When combining several map evaluation objectives that partially conflict with each other. Why: Some objectives pull in opposite directions, so no single map can satisfy all of them at once.
- [tradeoff] Direct evaluation is fast, simulation-based evaluation needs an AI to play part of the game, and interactive evaluation needs a human in the loop.
- [tradeoff] A representation must be expressive enough for truly novel games yet searchable, with local neighbourhoods and a density of good games; more expressivity makes search harder. When: When generating novel games with a game description language. Why: Searching needs nearby representations to behave similarly and enough good games scattered through the space.
- [tradeoff] Expressive range heatmaps support claims about variety, bias, and frequency, but they are aids for understanding and not perfect proofs of variety. When: When a generator can produce thousands or millions of distinct levels.
- [pitfall] Minimal variation yields non-expressive output, while random assembly of components yields senseless, unplayable content.
- [pitfall] Automatic generation can yield compelling play while producing content with weak visual appeal.
- [pitfall] An accessibility fitness that rewards smooth, vehicle-traversable ground drives evolution toward completely flat maps unless it is balanced by other measures. Why: Counterbalancing terms such as obstacle edge length stop flatness from dominating.
- [pitfall] Many evolved card game candidates turn out unplayable, so playability must be enforced in the encoding or the evaluation. When: When evolving card games in a description language that spans several known card games.
- [pitfall] Measures computed from rules alone did not improve agreement with human rankings, because a game's true character appears only in play. Why: A game's true character only emerges during actual play, so rule-only measures fail to track human judgments.
- [pitfall] Quality estimates from play trends are less reliable than playability measures, so they should not be trusted on their own.
- [pitfall] Treating connectivity alone as a sign of level quality is a mistake, since connected levels can still be poor. When: When random levels are generated sparsely so that nearly all of them are connected. Why: Sparse starts yield highly connected levels, and that over-connection makes them weak even though they are connected.
- [pitfall] Choosing a gameplay metric imports the designer's assumptions into evolution, and different metrics, such as survival time or shots fired, favour different content. When: When player preference is inferred from in-game actions instead of explicit selection. Why: The mapping from actions to preference is ambiguous, so the chosen action measure encodes designer assumptions.
- [pitfall] Assuming human and computer always have equal say is naive, because initiative is usually distributed unevenly. When: When humans and software co-create content in a mixed-initiative system. Why: Initiative shifts between them: sometimes the human brings the idea and the computer supports, and sometimes the reverse.
- [pitfall] Distance-based fitness prediction depends on how distance is defined, which biases the search, and long sprints amplify the error. When: When offline evolution estimates fitness of unseen individuals from user-rated ones by distance. Why: Distance assumptions could bias the search, so offline runs are kept to a few generations before new feedback.
- [pitfall] Using a metric highly correlated with an input parameter, such as difficulty as both input and metric, gives only confirmatory results and a false sense of insight. When: When a generator takes parameters that could also serve as evaluation metrics. Why: Expressive range evaluation aims to reveal emergent properties, which input-correlated metrics can only confirm.
- [pitfall] A hot spot in an expressive range chart reveals a generator bias, but the designer must still ask why the bias exists. When: When an expressive range heatmap shows concentrated clusters of output. Why: Hot spots reveal biased output, and the designer must then uncover what causes that bias.
- [pitfall] Implicit quality estimates assume that content which is selected, used, experienced or altered more during play is more valuable, which may not hold. When: When content quality is inferred from how players select, use, or alter it. Why: Direct end-user assessment has a core limitation: players may act as random content evaluators.

## dungeon layout and structure
- [model] A procedural dungeon generator usually has three elements: an abstract topology model, a construction method, and a geometry method, kept separate so each can be tested and changed alone.
- [model] A level can be a grid of rooms with start and end rooms, where adjacent rooms are joined by corridors.
- [model] Rooms are tile matrices drawn from predefined templates, where marked slot positions are replaced by multi-tile obstacles such as spikes or traps.
- [model] The FRP generator builds adventure modules in five stages: designer-required content, map search filling the rest, room detection, room graph construction, and room population. When: generating pen-and-paper style adventure maps. Why: Separating stages lets each be replaced by another method.
- [definition] Binary space partitioning recursively divides an area into smaller units, then connects them in order to form a dungeon.
- [definition] Separate-pass generation adds different content types in successive passes, each using simple rules with probabilities.
- [definition] Space partitioning subdivides a two- or three-dimensional space into disjoint cells, each point in exactly one cell, and applies the subdivision recursively to form a tree.
- [definition] A space tree is a discrete graph of location types that records the world's size, the number of unique locations, and which locations are adjacent.
- [mechanism] Weighted nodes enlarge a node's region so that it attracts more volume. When: When every node in a region layout can carry its own weight.
- [mechanism] The number of exits a room offers directly shapes where players go next, since they choose among those exits. When: Generating rooms and their connections. Why: A door signals an invitation to open it, and players are curious, so they go through one when little else is available.
- [mechanism] Forcing unavoidable time in each gameplay state produces hidden rooms off the main path that were not written in directly. When: when the level must force detours or backtracking.
- [mechanism] Distances between checkpoints are computed with dynamic programming, and the fitness function scores the level using them. When: fitness based on inter-room distances. Why: Shortest-path distances capture navigational structure of the level.
- [rule] Avoid narrow corridors and corners in generated dungeon layouts when camera collision is a concern. When: camera collision is a concern. Why: Camera clipping into level geometry undermines the player's sense of skill.
- [rule] Stage generated dungeon content in passes: outline the dungeon, describe it, lay out its map, then fill the map with content. When: Generating a dungeon.
- [rule] Procedural generators should enforce minimum passage widths and place light sources, so generated spaces stay navigable. Why: Light sources guide players through areas, and unlit spaces leave players without guidance.
- [rule] Forbid walls on tiles two steps from an altar, and give each altar four adjacent tiles. Why: Altars are meant to sit in open surroundings, so walls are kept out of the two-step ring.
- [rule] In the positive wall representation, keep maximum wall length small, around 5, since walls near the level diameter rarely give connected levels. Why: Walls near the level's diameter make connected levels unlikely.
- [rule] Once a square is marked as part of a room, it is no longer empty, which keeps rooms disjoint. When: detecting rooms in a grid map. Why: Marking prevents a square from belonging to two rooms.
- [rule] Use vertical elements such as columns or doorframes to frame generated room entrances and exits. When: when generating room entrances and exits. Why: Framing makes openings readable as transitions.
- [heuristic] RPG dungeons need lock-and-key puzzles, bonus objectives, multiple paths, and dead ends with ability-gated areas, which graph structures express more easily than strings. When: when generating explorative adventure or dungeon levels. Why: Explorative games depend on branching and gated progression. (x2)
- [heuristic] A fixed set of same-size tiles can be combined to form maze-like layouts. When: Generating or assembling maze layouts. Why: Uniform tile sizes make the pieces interlock predictably.
- [heuristic] Generated levels must provide connected spaces that characters can traverse, because movement AI depends on that connectivity to reach targets. When: Procedurally generated levels with AI characters. Why: Movement AI needs routes around obstacles and between rooms, so the level's spaces must link up for characters to reach their targets.
- [heuristic] A hub with landmarks pointing in several directions sends players outward toward several rooms or corridors. When: Laying out a central area with multiple exits. Why: Visual landmarks draw the eye first and the feet after, so players follow the cues without being told where to go.
- [heuristic] Room and corridor dimensions relative to avatar speed change the feel of control, so generated layout sizes matter. When: When generating spaces for an avatar with a set movement speed. Why: Spacing defines the feel of motion; objects packed tightly against the avatar's movement make play feel clumsy and oppressive.
- [heuristic] A procedural dungeon fills rooms with many monsters, items and encounters, so the variety of behavior these patterns address applies directly. When: When a game must define many inhabitants, items and quests, each with distinct behaviour. Why: Such games need far more behaviour than typical software, and these patterns let designers define and refine it quickly while keeping it maintainable.
- [heuristic] Use agent digging when organic, chaotic or cave-like layouts are wanted, or when the player should not easily predict the layout. When: When organic, chaotic or cave-like layouts are wanted rather than neatly organised rooms. Why: The layout depends on the agent's behaviour parameters, which are hard to predict without trial and error, so results are unpredictable.
- [heuristic] Use topology-first, two-stage generation when the room layout should be fixed before geometry is produced. When: When a level's room topology must be fixed before any geometry is produced.
- [heuristic] Use separate generation passes when content types can each be added with simple probabilistic rules.
- [heuristic] Generated spaces feel insubstantial without goals and context, so a generated dungeon may need a quest or story reason for its layout and encounters. When: Generating dungeons. Why: Unanchored generated worlds lack meaning or motivation for the player, so their content becomes insubstantial and tedious.
- [heuristic] Use required content when the designer must guarantee specific rooms, such as a boss area, inside a generated level. When: designer needs fixed areas in generated dungeons. Why: Required blocks keep key rooms while search fills the rest.
- [heuristic] Place exits to the next level in the last layer of a breadth-first room traversal. When: populating a dungeon graph with a multi-level structure. Why: The deepest layer is the furthest point from the entrance.
- [heuristic] Using see-through partitions between rooms lets a generated layout show a goal while still requiring the route to it. When: when generating room layouts. ## terrain generation
- [model] Terrain generation has two remedies: make terrain smooth by construction, or define a smoothness criterion and optimise the terrain against it.
- [model] Terrain generation methods include gradient-based (slopes first, then heights), fractal or noise-based (heights at several scales), agent-based (multiple feature types), and search-based (constraint satisfaction). When: Agent-based for multi-feature environments; search-based when gameplay constraints such as traversability apply.
- [definition] A heightmap is a two-dimensional matrix of real numbers where each cell stores one number giving the terrain height above a baseline at that point.
- [definition] 1/f noise sums noise at frequency f, plus half of the noise at 2f, a quarter at 4f, and so on.
- [definition] Fractional Brownian motion is a random walk with specified statistics, used as the underlying concept for fractal terrain, and practical methods approximate it. Why: Exact random walks are too expensive to compute directly.
- [definition] Genetic terrain programming evolves an expression tree that maps each map coordinate to a height value.
- [definition] Gradient noise assigns random slopes rather than random heights to lattice points, and derives heights from those slopes.
- [definition] Noise adds small variations to a surface, such as cloud cover, settled dust, water, fire, or skin and fur colouring.
- [mechanism] Terrain with detail at only one frequency looks artificial; generating heights at several scales looks more natural, as in diamond-square. Why: Natural landscapes vary at many sizes, and zooming in reveals similar variation at smaller scales.
- [mechanism] Larger roughness values produce rougher terrain and smaller values produce smoother terrain, because roughness sets the magnitude of the random offsets. Why: Roughness scales every random value added in the diamond and square steps.
- [mechanism] Mountain agents act only on terrain above a threshold, raising V-shaped ridges along random paths that turn within 45 degrees, producing zigzag ridgelines. When: Map regions above a set altitude, which beach agents leave untouched. Why: Occasional random turns of up to 45 degrees from the current heading bend the agent's path into a zigzag.
- [mechanism] Mountain agents also build perpendicular foothills off their ridges.
- [mechanism] Fractal terrain sums noise layers at increasing frequency, and layers at larger scales get larger amplitude. Why: Large features such as mountains rise more than small features such as boulders.
- [mechanism] An expression-based terrain can be enlarged or zoomed by querying the program at new coordinates, with no change to the program. When: When the map resolution is increased or the map is expanded. Why: Each cell is computed by querying the program with its own coordinates, so the output scales with no change to the program.
- [mechanism] Peaks and valleys emerge from rising and falling slopes rather than sitting on lattice points, so gradient noise looks more organic and shows no grid pattern. Why: Peaks and valleys come from changing slopes between lattice points, so they are not tied to the grid spacing.
- [mechanism] Smoothing the rate of change of gradient noise gives an extra level of smoothness compared with smoothing heights directly. Why: Interpolating slopes rather than heights means the rate of change is what gets smoothed, so slopes change gradually.
- [mechanism] Bilinear interpolation produces straight-line slopes and sharp peaks and valleys, which look like a child's drawing of mountains. Why: Each slope is a straight segment joining neighbouring random peaks and valleys, so no curvature appears.
- [mechanism] Mountains bound traversable space and block line of sight, so terrain shapes where players can go and what they can see. When: Open-world terrain with both aesthetic and mechanical roles. Why: Elevation features act as walls and occluders.

When: Whenever a user adds a new feature such as a city or river. Why: Sketched edits appear live in 3D, so each addition must be merged into neighbouring terrain.

## grammar generation
- [model] Grammars expand an axiom through production rules to generate plant structures, action-adventure levels, physical structures and missions; the grammars themselves can be evolved.

- [definition] A generative grammar is a finite set of recursive production rules that expand an axiom into larger structures until only terminal symbols remain; sampling it yields new instances.

- [definition] A formal grammar consists of rules that rewrite strings beginning at a start symbol; each rule swaps a left-hand side pattern for a right-hand side.
- [definition] A deterministic grammar has exactly one applicable rule per symbol, while a nondeterministic grammar may have several, so a selection method such as random choice, per-rule probability, or parameters is needed.
- [definition] An L-system is a grammar that expands all symbols simultaneously, producing strings with repeating structure.

- [procedure] For finite generators, count all variations; for infinite ones, increase the sample size until the charts match the previous smaller sample. - [pitfall] Fully random placement of monsters and traps gives variety at the cost of designer control.

- [fact] Quantities where most individuals score low and a few score high usually follow a power law, controlled by a single exponent that sets how flat the curve is. Why: Money among people is a typical example.
- [fact] RANDBETWEEN(min,max) returns a whole number from min to max inclusive, so RANDBETWEEN(1,1024) selects one row of a 1024-row table.
- [fact] Random-number formulas such as RAND() and RANDBETWEEN() re-roll every time the sheet updates, so one roll must be pasted as values to keep it. When: Generating random content in a spreadsheet. Why: Recalculation regenerates random formulas on each update.
- [fact] Players can be served a sequence of games sampled from one constrained space and work out the shared rules behind them.

## agent playtesting and logs
- [rule] Map each log entry to its node by localization and add a connection where the log shows direct movement between two nodes; points-of-visibility is faster but can miss links around corners. - [heuristic] Attention is limited, so generated content competes for the small share of focus a player can spare. Why: Listeners attending to one stream retain almost nothing from another, so spare attention is scarce.

- [metric] Automatic explorers are run only a couple of game minutes at most because they get stuck. When: When an automatic character explores a level to build a log. Why: Automatic explorers tend to jam and keep revisiting one small region of the map.

## constraint-based generation
- [definition] Constraint-driven generation places assets by designer-defined relationships, such as chairs placed around tables.
- [mechanism] A level is rejected if any alternative solution uses the same level-design atoms but fails the concept condition.
- [mechanism] When a generator guarantees every output is playable, playtesting can shift from checking reachability to judging fun. When: when the generator enforces playability constraints.
- [rule] Constrain generated rules to forbid unwinnable states, such as losing all objects of one kind while others remain, and to require winnable interactions.
- [rule] Write theming and consistent design rules into the generator so procedurally placed elements stay architecturally coherent rather than purely random. Why: Purely random placement can break architectural coherence.
- [procedure] 1) Sort chunks by priority, coordinates, and type. 2) When two chunks overlap, keep the higher-priority one and remove the other. 3) Priority order is hills with bill blasters or piranha plants, blank hills, platforms with enemies, blank platforms, then coins and blocks. When: when post-processing a generated level with overlapping chunks. Why: Ordering by priority gives a deterministic way to remove conflicts.
- [fact] Many content generation tasks, such as puzzle levels, can be framed as constraint-solving problems and encoded in Answer Set Programming as logical rules a solver satisfies.
- [fact] The game engine and non-player character behaviour are excluded from what counts as content.
- [fact] A constraint solver returns rule sets that satisfy hard constraints, rather than maximising an evaluation score.

## generated object and asset design
- [mechanism] When found items supply most of the power, the base values of items a generator places largely set the power curve. When: generating items for a progression game. Why: Generated base values are the main source of power differences.
- [mechanism] A Gaussian distribution clusters decorations near a location's centre, so neighbouring locations blend into each other. When: Placing decorations in a location. Why: Decorations cluster toward the centre, so decorations from adjacent locations spill over and blend at their borders.

- [rule] Generated assets should share one stylistic language across visuals and sound so procedural content feels like part of one world. When: when generating visual and audio assets procedurally. Why: Consistent style across senses keeps generated content believable.
- [rule] Set a generator's reward density deliberately, because randomly generated spaces with frequent loot drops are a direct source of the acquisition emotion. When: When generating dungeons or levels with loot. Why: Reward density directly shapes the feeling of acquisition.
- [rule] Give generated interactive objects a look distinct from static walls and props so players can identify them. When: when generating dungeon or level content.
- [heuristic] A generator needs to supply only the details a player cannot reasonably infer from what is already present. When: when generating content for a player to experience. Why: Players fill unstated gaps themselves, so surplus detail is wasted effort.
- [heuristic] A generator that creates many variants from one base type should keep variant stats in data rather than in a separate subclass per variant. - [procedure] 1) Draw the outermost layer first. 2) Draw each inner layer on top, scaled by depth. 3) Use one network for all layers so they share regularities. When: generating multi-layer shapes with one CPPN. Why: Shared network regularities mirror how real layered structures relate.

## constructive generation methods
- [definition] Constructive generation makes content in one pass, producing one output per run in a fixed, usually short time without evaluating or regenerating the output.
- [rule] Author hand-designed scenes as modular pieces for a constructionist generator to assemble at random into varied levels.
- [heuristic] Most constructive methods are simple to implement and can often be adapted from dungeons to other content types. Why: Running in fixed time without scoring output keeps these methods simple.
- [heuristic] Constructive methods suit roguelikes and certain platformers where predictable, short runtime matters. Why: Output is never scored or regenerated, so runtime stays fixed.
- [tradeoff] Constructive methods run in predictable, short time but offer limited control, making output hard to steer toward specific design goals, unlike search-based methods that evaluate and regenerate output.
- [fact] Cellular automata and other constructive algorithms can generate roguelike dungeons and similar 2D navigation levels.
- [fact] Constructive dungeon methods form five families: space partitioning, agent-based digging, cellular automata, generative grammars, and separate passes of probabilistic rules.
- [fact] Constructionist generation pairs well with architectural pattern languages, since both assemble reusable spatial units.

## cppn indirect encoding

## board and card game generation
- [procedure] 1) Restructure data so each deal and its outcome sit in a single row. 2) Fill down formulas for as many rows as there are initial deals. 3) List every distinct initial deal, one per row. 4) Sort rows by win probability. 5) Pick the deal(s) whose win probability is nearest 0.5. - [procedure] 1) Encode each complete game as a string read into rules by a compact description language. 2) Play it with a minimax agent whose evaluation function is tuned for that game. 3) Measure game length, draw rate, and rule count. 4) Combine these with a weighted sum whose weights come from successful games. When: evolving complete game rule sets. Why: Weights were derived from empirical study of traits found in successful board games.
